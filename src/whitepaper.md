# Optimizing LLM Inference with Key-Value Caching

*A survey of how the key-value (KV) cache shapes LLM serving latency, throughput and memory, from on-GPU paging to offload onto CPU memory and storage.*

## Introduction

Large Language Model (LLM) inference proceeds in two phases: a **prefill** phase, in which every prompt token is processed in a single parallel forward pass to populate the model's internal state, and a **decode** phase, in which output tokens are generated one at a time, each conditioned autoregressively on every token generated or supplied so far [@databricks; @instinfer]. This two-phase structure – more than model size alone – is what makes latency and throughput engineering for LLM serving qualitatively different from serving a single dense forward pass, and it is why two distinct latency metrics are used to describe it [@databricks; @nim-metrics]:

* **Time to First Token (TTFT):** the latency from request submission to the emission of the first output token, including any queuing delay [@nim-metrics]. TTFT is driven primarily by the cost of the prefill pass over the prompt (below), plus tokenization and network overhead [@nim-metrics].

* **Time Per Output Token (TPOT):** the average latency between successive output tokens during decode. NVIDIA's NIM benchmarking documentation treats TPOT as synonymous with **Inter-Token Latency (ITL)**, defined as end-to-end request latency minus TTFT, divided by (total output tokens − 1) [@nim-metrics]. MLPerf's inference rules use the same two-metric split – TTFT for the first token, TPOT for "the average interval between all the tokens generated" thereafter – and attach numeric targets to each, per model and per deployment scenario: for example, Llama-3.1-8B's "server" scenario (termed the "Conversational" category in the current rules document) requires TTFT ≤ 2 s and TPOT ≤ 100 ms, tightened to TTFT ≤ 0.5 s and TPOT ≤ 30 ms for its "interactive" scenario (the document's "Interactive" category) [@mlcommons-2025-llama31bench; @mlcommons-2026-inferencerules]. Not every benchmarking tool agrees on whether the first token is included in the TPOT/ITL average, so reported numbers are not always bit-for-bit comparable across tools even when both are computed correctly [@nim-metrics].

End-to-end request latency is then approximately $\text{TTFT} + \text{TPOT}\times(N_{out}-1)$ for an $N_{out}$-token completion, following NIM's ITL-based accounting [@nim-metrics] – Databricks' own formulation instead uses the simpler $\text{TTFT}+\text{TPOT}\times N_{out}$, without subtracting the first token [@databricks], though the difference is one TPOT term and is usually negligible for long completions – and system throughput is the aggregate output-token rate across all concurrent requests [@databricks]. TTFT and TPOT trade against each other under a fixed compute budget – batching more requests raises aggregate throughput but lengthens the queuing and cross-request interference each individual request experiences – so a serving system cannot be judged on throughput alone. DistServe introduces **per-GPU goodput** to capture this: the maximum request rate a system can sustain *per GPU provisioned* while a target fraction of requests (e.g., 90%) meet *both* a TTFT and a TPOT service-level objective (SLO) at once – the per-GPU normalization is deliberate, since it is what lets goodput compare configurations that use different numbers of GPUs on a cost-per-query basis [@distserve]. This SLO-attainment framing has moved from research into production tooling: NVIDIA's Dynamo serving stack, for instance, ships an autoscaler ("Planner") that sizes prefill and decode worker pools directly against configured TTFT/ITL targets rather than against raw queries-per-second [@nvidia-2025-dynamo].

A central enabler of low TPOT is the **Key-Value (KV) cache**: storing the attention key and value tensors computed for each past token so they can be reused rather than recomputed at every later generation step [@instinfer]. The KV cache is the reason decode-phase per-token cost does not grow with the *square* of context length the way naive re-computation would (below), and it is also the reason GPU memory, not GPU compute, becomes the binding constraint on how many requests can be served concurrently at long context (later sections). This whitepaper follows the cache down the memory hierarchy and out across the data center. It covers the mechanics of KV caching and its precise effect on TTFT and TPOT; on-GPU memory management (paging, kernels, quantization); three ways to make the cache smaller or cheaper – attention architectures that shrink it at the source, compression and eviction, and reuse across requests; offload to CPU memory and SSDs; disaggregated serving that moves the cache between machines; shared and persistent storage tiers for the cache; how these strategies evolved at scale and which workload trends now drive KV demand; how to measure and price cache effects; the security and integrity risks of shared caches; and, finally, the cache as an editable model state rather than only a performance structure. Appendix A describes a sizing calculator that reproduces the paper's KV-size arithmetic. Where a figure comes from a single vendor or paper, it is reported as such, together with the model, hardware, and baseline used to produce it – KV-cache-driven speedups are highly sensitive to sequence length, batch size, and hardware generation, and do not transfer uncritically across settings.

## KV Cache Mechanics and Impact on Latency & Throughput

Self-attention, as originally specified, has per-layer computational complexity $O(n^2\cdot d)$ for a sequence of length $n$ and model width $d$, because every one of the $n$ query vectors must be compared against every one of the $n$ key vectors [@vaswani-2017-attention]. In autoregressive decoding this becomes wasteful if handled naively: a plain, cache-free re-invocation of the standard forward pass at each step recomputes attention over the *entire* growing prefix rather than reusing anything already computed for earlier tokens [@vaswani-2017-attention]. The **KV cache** removes this redundancy – "significantly reduc[ing] computational complexity by allowing the model to reference past information efficiently without time-consuming recomputations" [@instinfer] – by storing each layer's key ($K$) and value ($V$) tensors the first time they are computed and reusing them at every later step; only the new token's query, key and value need to be computed, and only the new query needs to attend against the stored history.

**Precise per-step complexity.** With the cache in place, a transformer layer's cost at decode step $t$ splits into two terms with different scaling behavior, and conflating them is a common source of error:

* The query/key/value/output projections and the feed-forward (MLP) block operate on exactly one new token, so their cost is $\Theta(d_{model}^2)$ per layer – **independent of context length** $t$ [@pope-2022-scaling; @kipply-2022-inference].
* The attention operation itself – the new query's dot product against all $t$ cached keys, then a weighted sum over the $t$ cached values – costs $\Theta(t\cdot d_{model})$ per layer, since $n_{heads}\cdot d_{head}=d_{model}$: this term **grows linearly with the number of tokens already generated or prefilled** [@pope-2022-scaling].

By contrast, a naive re-invocation of the full forward pass over the whole prefix at every step (i.e., without any cache, calling the model on the entire sequence so far and reading off the last position) recomputes the complete $t\times t$ self-attention matrix, costing $\Theta(t^2\cdot d_{model})$ per layer, on top of redundantly recomputing the $\Theta(t\cdot d_{model}^2)$ projections for every position in the prefix rather than just the new one [@vaswani-2017-attention; @instinfer]. So the familiar shorthand "caching drops per-step complexity from $O(n^2)$ to $O(n)$" is accurate as a statement about the *attention* term under this common form of cache-free decoding – it is not a statement about the projection/MLP term, whose $\Theta(d_{model}^2)$-per-token cost is unaffected by caching either way. What caching removes is the *redundant recomputation* of that term across steps (from $\Theta(t)$ back down to $\Theta(1)$ per step); it does not shrink the per-token cost itself.

**Time to First Token.** Prefill computes $K$, $V$ and $Q$ for all $n$ prompt tokens in one parallel pass. Its projection and feed-forward cost is $\Theta(n\cdot d_{model}^2)$ – linear in prompt length, since it is the same fixed per-token cost repeated $n$ times – but the self-attention operation over the full $n\times n$ score matrix costs $\Theta(n^2\cdot d_{model})$, quadratic in prompt length, exactly as in the original complexity analysis of self-attention [@vaswani-2017-attention; @pope-2022-scaling]. The two terms are of comparable magnitude when $n\approx d_{model}$: for prompts short relative to model width (roughly $n\lesssim d_{model}$, i.e., a few thousand tokens for a 4k–8k-wide model) the linear projection term dominates and TTFT scales close to linearly; once $n$ grows past that point, the quadratic attention term takes over and TTFT scales more steeply [@pope-2022-scaling]. Critically, **FlashAttention does not change this FLOP count for the forward pass relevant to inference.** It is an IO-aware, exact-attention *kernel*: tiling and recomputation reduce the number of reads and writes to GPU high-bandwidth memory (HBM) from $\Theta(Nd+N^2)$ to $\Theta(N^2d^2M^{-1})$ (where $M$ is on-chip SRAM size), which is what makes it dramatically faster and linear- rather than quadratic-memory in practice; the paper's own Theorem 1 gives the forward pass's cost as $O(N^2d)$ FLOPs, the same asymptotic class as standard attention [@dao-2022-flashattention]. (The paper's own benchmark figures show FlashAttention's *total* FLOP count – forward plus backward combined – is in fact slightly higher than standard attention's, because of recomputation in the backward pass; that is a training-time effect and does not apply to the forward-pass-only prefill/decode path this section concerns [@dao-2022-flashattention].) Its successor, FlashAttention-2 [@dao-2023-flashattention2] – accepted as an ICLR 2024 poster – further improves GPU occupancy and warp-level work partitioning to close more of the gap to peak matmul throughput, again without changing the asymptotic FLOP count. So "TTFT grows roughly linearly with prompt length" is at best a short-context approximation: it understates cost at long context, and the attention FLOP term stays quadratic with or without FlashAttention-class kernels.

Two mechanisms *do* cut, rather than merely accelerate, redundant prefill work. First, prefix caching lets a new request skip recomputing a prompt segment it shares with an earlier one: PagedAttention was designed from the outset to share KV blocks "within and across requests" via copy-on-write [@vllm-sosp], and this is now a separately documented production feature (Automatic Prefix Caching) – with the explicit caveat that it only ever shortens the prefill/TTFT portion of a request, never the decode/TPOT portion, and only when a genuine prefix match exists [@vllm-2025-apc]. Second, chunked prefill – introduced as "chunked-prefills" by Sarathi [@agrawal-2023-sarathi] and refined into the "stall-free scheduling" of Sarathi-Serve [@agrawal-2024-sarathiserve] – splits a long prompt's prefill into near-equal chunks interleaved with other requests' decode steps ("piggybacking"), so decode tokens are never blocked behind a full, uninterrupted prefill. This does not reduce FLOPs, and it is not free: splitting a prefill into $N$ equal chunks means each later chunk's attention must re-load every earlier chunk's KV cache from HBM, raising total KV-cache HBM traffic for that one prefill from $\Theta(N)$ (non-chunked) to $\Theta(N^2)$ in the number of chunks. DistServe's own analysis of the technique – which it attributes to Sarathi/Sarathi-Serve rather than claiming as its own – concludes that it "trades TTFT for TPOT and cannot eliminate the interference" between prefill and decode, only alleviate it [@distserve]. Chunked prefill is discussed further alongside prefill/decode disaggregation below [@splitwise; @distserve].

**Time Per Output Token and throughput.** Because the decode-step attention term costs $\Theta(t\cdot d_{model})$ while the projection/MLP term costs $\Theta(d_{model}^2)$ regardless of $t$, per-token latency in principle grows only slowly – linearly in context length, not quadratically – as generation proceeds. Whether that growth is visible in wall-clock time depends on which resource is the bottleneck, and for decoding on current data-center GPUs that resource is almost always **memory bandwidth**, not FLOPs. This follows from a simple arithmetic-intensity (FLOPs-per-byte) argument, in the tradition of Shazeer (2019) and Pope et al. (2022) [@shazeer-2019-mqa; @pope-2022-scaling]. Decode at batch size $B$ has two memory-traffic components per step: model *weights*, loaded once per step regardless of $B$ but used across $B$ matrix–vector products (so this component's arithmetic intensity rises with $B$, and at large enough batch this part of the step can become compute-bound), and the *KV cache*, where each of the $B$ sequences carries its own cache, so bytes read scale with $B$ just as the attention FLOPs performed against them do – leaving the ratio roughly constant, on the order of a few FLOPs per byte transferred, independent of batch size [@pope-2022-scaling]. On an NVIDIA H100 SXM (989.5 TFLOPS dense BF16 Tensor Core throughput; 3.35 TB/s HBM3 bandwidth) [@nvidia-2023-h100], the chip is compute-bound only above roughly $989.5\times10^{12}/3.35\times10^{12}\approx295$ FLOPs per byte. The same arithmetic on a newer NVIDIA B200 SXM (2.25 PFLOPS dense BF16 Tensor Core; 7.7 TB/s HBM3e) gives a nearly identical balance point, $\approx292$ FLOPs per byte [@nvidia-2025-b200]: despite roughly 2.3$\times$ higher absolute compute and bandwidth on B200, the compute-to-bandwidth *ratio* that determines whether decode is memory-bound is essentially unchanged across this hardware generation, so the argument below is not an artifact of H100-specific numbers. KV-cache reads sit one to two orders of magnitude below that threshold at any batch size, which is why growing the batch size raises aggregate throughput – by amortizing weight loads over more sequences – without proportionally shrinking the marginal cost of reading each sequence's own KV cache, and why, at large batch or long context, KV-cache bandwidth rather than weight bandwidth becomes the binding constraint on decode throughput [@pope-2022-scaling; @micron]. This is also the underlying motivation for multi-query and grouped-query attention (below): shrinking the KV cache directly raises decode arithmetic intensity, since less data must be re-read per token [@shazeer-2019-mqa; @ainslie-2023-gqa].

**Memory footprint of the cache.** The cache must store, for every cached token, a key and a value vector per layer per *KV head* – not per query head, and the distinction matters. Under plain multi-head attention (MHA), the number of KV heads $n_{kv}$ equals the number of query heads, but multi-query attention (MQA) shares a single KV head across all query heads ($n_{kv}=1$) [@shazeer-2019-mqa], and grouped-query attention (GQA) uses an intermediate number of KV heads, $1<n_{kv}<n_{heads}$, trading a small quality cost for most of MQA's bandwidth savings [@ainslie-2023-gqa]. The correct per-token cache size is

$$\text{bytes/token} = 2\cdot L\cdot n_{kv}\cdot d_{head}\cdot s,$$

where $L$ is the number of layers, $d_{head}$ is the per-head dimension, the leading 2 accounts for storing both $K$ and $V$, and $s$ is the number of bytes per stored element (2 for fp16/bf16, 1 for fp8/int8 – see the next section) [@shazeer-2019-mqa; @pope-2022-scaling; @kipply-2022-inference]. This reduces to the more familiar $2\cdot L\cdot d_{model}\cdot s$ only in the MHA special case, where $n_{kv}\cdot d_{head}=d_{model}$; substituting total hidden size $d_{model}$ for $n_{kv}\cdot d_{head}$ silently assumes MHA, overstating the cache size of any modern GQA/MQA model, and omitting the bytes-per-element factor $s$ silently assumes a fixed dtype, which breaks under KV quantization.

As a worked example, Llama 3 8B uses $L=32$ layers and $d_{model}=4096$ split across 32 query heads ($d_{head}=128$), but only $n_{kv}=8$ KV heads under GQA, stored in bf16 ($s=2$ bytes) [@meta-2024-llama3]. Its per-token KV cache is $2\times32\times8\times128\times2=131{,}072$ bytes $=128$ KiB, so an 8,192-token sequence at batch size 1 occupies $128\text{ KiB}\times8{,}192\approx1\text{ GiB}$. Had the same architecture used full MHA ($n_{kv}=32$) instead of GQA-8, the identical context would cost four times as much – about 4 GiB – since GQA-8's KV-head count is $4\times$ smaller than its query-head count [@meta-2024-llama3; @ainslie-2023-gqa]:

**Illustrative per-token KV cache size by attention variant (bf16, 8,192-token context, batch size 1)**

| Attention variant | Example | $L$ | $n_{kv}$ | $d_{head}$ | Bytes/token | @ 8K context |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| MHA ($n_{kv}=n_{heads}$) | Llama 3 8B, hypothetically with MHA-32 | 32 | 32 | 128 | 512 KiB | ≈4.0 GiB |
| GQA-8 (actual) | Llama 3 8B [@meta-2024-llama3] | 32 | 8 | 128 | 128 KiB | ≈1.0 GiB |
| MQA ($n_{kv}=1$) | Illustrative, same layer/head-dim shape | 32 | 1 | 128 | 16 KiB | ≈128 MiB |

These figures are per sequence at batch size 1; the aggregate cache scales linearly with batch size and with the number of concurrent sequences, which is what actually strains GPU memory in production (discussed later). They also do not capture more aggressive current compression schemes: DeepSeek-V2's Multi-head Latent Attention (MLA) projects $K$ and $V$ into a shared low-rank latent vector rather than storing per-head tensors, which DeepSeek reports – vendor-benchmarked, relative to their own dense 67B predecessor within the same model family – cuts KV cache size by 93.3% and raises maximum generation throughput by 5.76$\times$ [@deepseek-2024-mla]. That is a substantially larger reduction than GQA alone provides, at the cost of a more invasive architecture change that, unlike GQA, cannot be retrofitted onto an existing MHA checkpoint by simple mean-pooling of heads [@ainslie-2023-gqa; @deepseek-2024-mla].

In summary: KV caching removes the *redundant* recomputation that would otherwise make per-token cost grow quadratically with generation length, but it does not remove the inherent quadratic FLOP cost of a single full-context attention pass, does not by itself change whether a workload is compute- or memory-bound, and its memory footprint depends on the number of KV heads and the storage dtype, not on model width alone. Fitting the resulting cache into – and moving it efficiently through – the GPU memory hierarchy is the subject of the next section.

## On-GPU KV Cache: Memory Efficiency and GPU Utilization

Keeping the KV cache in GPU high-bandwidth memory (HBM) is the fastest configuration available, but "fast" needs a concrete number. HBM bandwidth on current NVIDIA data-center GPUs is not "hundreds of GB/s" — it is in the low single-digit terabytes per second, and it varies substantially by generation:

| GPU (SXM) | HBM generation | Capacity | Peak bandwidth |
| --- | --- | --- | --- |
| H100 | HBM3 | 80 GB | 3.35 TB/s |
| H200 | HBM3e | 141 GB | 4.8 TB/s |
| B200 | HBM3e | 180 GB | up to 8 TB/s |
| B300 / GB300 ("Blackwell Ultra") | HBM3e | up to 288 GB | up to 8 TB/s |

[@nvidia-2023-h100; @nvidia-h200; @nvidia-2026-hgx-blackwell]. NVIDIA's own collateral is not fully consistent on the B300 figure: the standalone Blackwell Ultra datasheet lists 279 GB of HBM3E per GPU, while NVIDIA's HGX reference-architecture documentation and OEM datasheets list up to 288 GB. The 279 GB figure is the more internally consistent of the two: the same Blackwell Ultra datasheet separately states 20 TB of HBM3E across a 72-GPU GB300 NVL72 rack, and $279 \times 72 \approx 20.1$ TB matches that figure, whereas $288 \times 72 \approx 20.7$ TB would not round to "20 TB" [@nvidia-blackwell-ultra; @nvidia-2026-hgx-blackwell]. Even the low end of the per-GPU bandwidth range, 3.35 TB/s, is roughly 26× the ~128 GB/s theoretical peak of a PCIe Gen5 x16 link [@nvidia-2023-h100] — the gap that motivates keeping the cache on-GPU rather than reaching across PCIe. Achieved KV-cache offload throughput in practice runs well below that theoretical peak — 16–36 GB/s in the measurements discussed in the next section [@instinfer] — reflecting protocol overhead and largely unidirectional transfer patterns, but even that reduced figure leaves on-GPU HBM roughly two orders of magnitude faster. When the entire cache fits in GPU memory, each new token's attention reads prior keys/values at the full HBM rate [@instinfer], avoiding host transfers and their added latency; in a GPU-only setup the decode phase can sustain near-peak throughput until memory capacity, not compute, becomes the limit.

The KV cache's footprint follows directly from model architecture. For $L$ transformer layers, key/value heads of combined width $H_{kv} = n_{kv} \times d_{head}$ (equal to the full hidden size under multi-head attention, but far smaller under grouped-query or multi-query attention, which most current models use), $p$ bytes per stored value, batch size $B$, and sequence length $S$, the cache size in bytes is $2 \cdot L \cdot H_{kv} \cdot p \cdot B \cdot S$, the factor of 2 covering both keys and values. Two examples show the scale this reaches in practice. A 13B-parameter model with Llama-2-13B's published architecture ($L=40$, multi-head attention with 40 heads of dimension 128, so $H_{kv}=5{,}120$) [@touvron-2023-llama2], at batch size 32 and a 4,096-token context in FP16/BF16 ($p=2$ bytes), gives $2 \times 40 \times 5{,}120 \times 2 \times 32 \times 4{,}096 \approx 107$ GB of KV cache against roughly 26 GB of FP16 weights — a ratio near 4×, consistent with the commonly cited "~100 GB, ~4×" figure for this configuration [@instinfer]. A Llama-3-8B-class model with grouped-query attention ($L=32$, 8 KV heads of dimension 128, so $H_{kv}=1{,}024$ versus 4,096 for its 32 query heads — a 4× reduction from GQA alone) [@meta-2024-llama3], at batch size 1 and a 1-million-token context, gives $2 \times 32 \times 1{,}024 \times 2 \times 1{,}000{,}000 \approx 131$ GB of KV cache by this formula (decimal GB; $\approx 122$ GiB) — close to but not identical to HeadInfer's own reported figure for exactly this model and context length, which the paper states directly rather than deriving from this formula: 128 GB of KV cache, 15 GB of FP16 weights and 64 GB of activation memory, for a 207 GB total baseline GPU memory requirement, before their head-wise offloading reduces this to 1 GB of KV cache and 17 GB of total GPU memory [@headinfer]. Both figures far exceed any single GPU's HBM capacity in the table above, which is why naive GPU-only caching is infeasible at these context lengths or batch sizes without the techniques below.

Even short of hitting capacity limits, allocation inefficiency degrades utilization. vLLM's original analysis found that systems pre-allocating a contiguous block for each sequence's worst-case length wasted 60–80% of reserved KV memory to fragmentation and over-reservation [@vllm-blog]. PagedAttention addresses this by partitioning each sequence's KV cache into fixed-size blocks that need not be contiguous in memory, analogous to OS virtual-memory paging; the vLLM team reports this reduces waste to under 4%, and its block-table indirection additionally enables copy-on-write sharing of a common prompt prefix across parallel completions, cutting memory use in such cases by up to 55% and, in the vLLM team's own measurement, improving throughput by up to 2.2× [@vllm-blog]. The peer-reviewed SOSP evaluation of this same mechanism reports the memory-saving figure independently — 37.6–55.2% on Alpaca and 44.3–66.3% on ShareGPT, depending on beam width — and a corresponding 1.3–2.3× throughput improvement for beam search specifically over a strong Orca (Oracle) baseline; this is consistent with, but not identical to, the blog's 2.2× figure, which the paper's own evaluation section does not itself restate [@vllm-sosp].

KV cache quantization has moved from research technique to a stable, documented feature of production serving engines. FP8 KV cache is supported as a first-class option — not merely a research patch — in vLLM (`kv_cache_dtype="fp8_e4m3"`/`"fp8_e5m2"`, with per-tensor or calibrated per-attention-head scales) [@vllm-fp8], in SGLang (`--kv-cache-dtype fp8_e4m3`/`fp8_e5m2`) [@sglang-kvcache], and in NVIDIA TensorRT-LLM, which can enable FP8 KV cache even for checkpoints not quantized with it [@nvidia-trtllm-quant]. On Blackwell GPUs (compute capability sm100/sm103), TensorRT-LLM additionally supports an NVFP4 KV cache — a 4-bit floating-point format with fine-grained block scaling, requiring offline calibration through NVIDIA's TensorRT Model Optimizer — which NVIDIA reports cuts KV cache memory by roughly 50% versus FP8 (approximately doubling addressable context or batch size at fixed memory) with under 1% accuracy loss on LiveCodeBench, MMLU-Pro, MBPP and Ruler-64K for the models the vendor tested, though values must still be dequantized to FP8 before the attention matmul itself, and Hopper GPUs do not support this path [@alvarez-2025-nvfp4kv; @nvidia-trtllm-quant]. These are vendor-reported numbers specific to the cited models, hardware and calibration data, not a general accuracy guarantee, and coverage is uneven: sliding-window and other non-standard attention layers are flagged as more quantization-sensitive and can be selectively excluded in vLLM [@vllm-fp8]. Independently of vendor formats, academic work has pushed further to 2 bits: KIVI applies per-channel quantization to keys and per-token quantization to values and reports "almost the same quality" — a qualitative claim in the paper's own framing rather than a stated accuracy bound — on Llama, Falcon and Mistral models, with 2.6× lower peak memory (including model weights), up to 4× larger batch size, and 2.35–3.47× higher throughput on the workloads tested [@kivi]; note that the frequently repeated "8×" figure for KIVI refers only to the KV tensor's own bit-width reduction (16-bit to 2-bit), not to these more modest end-to-end memory and throughput numbers. LogQuant compresses selectively along an observed log-distributed attention pattern and reports 25% higher throughput and 60% larger batch size at fixed memory, with 40–200% better accuracy on math and code-completion tasks specifically than the two baselines LogQuant's own comparison names — the 2-bit quantizer KIVI and the eviction-based method H2O — at matched compression; because H2O evicts tokens outright rather than quantizing them to any bit-width, this is a comparison against other aggressive KV-compression strategies generally, not narrowly against other 2-bit quantizers, and not against uncompressed FP16 [@logquant]. Neither paper establishes that these results hold for much larger models, mixture-of-experts architectures, or multi-million-token contexts, where quantization error accumulates over far more attended tokens; production deployments should validate accuracy on their own task and context-length distribution before adopting 2-bit KV caches, the same caution NVIDIA gives for its own 4-bit format [@alvarez-2025-nvfp4kv].

Neither paging nor quantization delivers its throughput benefit without attention kernels and a scheduler built to exploit them. FlashAttention computes exact attention via tiling and online softmax to minimize HBM reads and writes, making attention IO-bound by design rather than wasteful of bandwidth by default [@dao-2022-flashattention]. Because a decode step has query length 1, however, plain FlashAttention under-utilizes the GPU's streaming multiprocessors at the small batch sizes long contexts force; Flash-Decoding addresses this by additionally parallelizing over the KV sequence-length dimension, reporting up to 8× faster decoding at long context lengths in the authors' CodeLlama-34B benchmarks [@dao-2023-flashdecoding]. FlashInfer generalizes further into a JIT-compiled, block-sparse attention engine built to handle vLLM's and SGLang's paged, non-contiguous KV-cache layout natively; the authors report 29–69% inter-token-latency reduction against a compiler-backend baseline, 28–30% latency reduction for long-context inference, and 13–17% speedup for parallel generation in their own A100/H100 benchmarks, and it is integrated into vLLM, SGLang and MLC-Engine [@ye-2025-flashinfer]. On the scheduling side, continuous (iteration-level) batching — introduced by Orca, which schedules admission and eviction every model iteration rather than every batch, via "selective batching" that lets requests at different sequence positions and phases share a single batched forward pass — is what lets a paged KV-cache manager actually keep GPU occupancy high as requests arrive and finish at different times; Orca reports a 36.9× throughput improvement over NVIDIA FasterTransformer at matched latency on GPT-3 175B [@yu-2022-orca]. That multiplier is measured against a 2022 non-continuous-batching baseline and should be read historically rather than as a live benchmark: vLLM, TGI, SGLang and TensorRT-LLM all now implement continuous batching as standard practice, and it is this combination — IO-aware kernels, paging, quantization and iteration-level scheduling together — rather than any single technique that produces the throughput reported below.

When the cache fits well in GPU memory and is efficiently managed, decode becomes bandwidth-bound against the HBM figures above rather than compute-bound. A Micron engineering analysis of Llama-2-70B inference on an HGX H100 system found throughput scaling near-linearly with batch size until the KV cache saturates memory capacity or bandwidth, after which throughput collapses or the process fails with an out-of-memory error [@micron]; the qualitative pattern generalizes, but the specific batch size at which it occurs is tied to that model, GPU and sequence-length configuration and does not transfer directly to other models or to the higher-bandwidth H200/B200/B300 parts above. The clearest historical demonstration that memory management, not raw compute, was the binding constraint came from vLLM's June 2023 introduction of PagedAttention, which reported up to 24× higher throughput than a then-current, non-batching HuggingFace Transformers baseline and 2.2–3.5× over HuggingFace TGI on LLaMA-7B/13B with ShareGPT-length requests (Table 1) [@vllm-blog]. That 24× figure should be read as a 2023-era historical marker rather than a claim about today's alternatives: it compares against a serving stack that itself lacked continuous batching, and vLLM's own peer-reviewed SOSP evaluation reports a more modest — but still substantial — 2–4× improvement over stronger, already-batching baselines (FasterTransformer and Orca) at matched latency [@vllm-sosp]. The durable claim both papers support is not the specific multiplier but the underlying one: GPU memory management, not FLOPs, was the binding constraint on 2023-era LLM serving throughput, and closing that gap — via paging, quantization, and the kernels and schedulers above — is what let GPU compute utilization approach its ceiling.

In summary, keeping the KV cache on-GPU and managing it with paging, quantization and IO-aware kernels under a continuous-batching scheduler yields the best achievable TTFT and TPOT on current hardware: the first token emerges as soon as prefill completes, and subsequent tokens stream at a rate bounded by HBM bandwidth — 3.35 to roughly 8 TB/s on current NVIDIA GPUs — rather than by avoidable memory waste. GPU HBM nonetheless remains scarce and expensive relative to host memory or storage, and the worked examples above show it exhausted by context lengths and batch sizes well within current production workloads. We next examine what happens, and what it costs, when the cache is pushed beyond GPU memory entirely.

## Shrinking the Cache at the Source: Attention Architectures

The preceding sections treat the number of key/value heads, head dimension and layer count as fixed properties of "the model" and optimize everything downstream – paging, quantization, offload. Those three numbers are themselves architectural choices, and since 2019 they have been the largest lever on KV cache size: for a dense transformer, KV bytes per token scale as

$$\text{KV bytes/token} = 2 \cdot L \cdot n_{kv} \cdot d_h \cdot s$$

where $L$ is the number of layers, $n_{kv}$ the number of key/value heads, $d_h$ the head dimension, and $s$ the bytes per stored element (2 for bf16/fp16, 1 for int8/fp8). The factor of 2 is for the separate key and value tensors. Every technique in this section attacks one of $n_{kv}$, $L$, or the "2×" itself, either by sharing heads, sharing across layers, compressing K and V into a joint latent, or replacing most layers' attention with a fixed-size recurrent state.

### Fewer heads to cache: MQA and GQA

Shazeer's multi-query attention (MQA) lets all query heads share a single key/value head, cutting $n_{kv}$ to 1 and the KV cache by a factor of $h$ (the original head count), at the cost of a measurable quality drop and a model that generally must be trained (or "uptrained") for it from the start [@shazeer-2019-mqa]. Grouped-query attention (GQA) interpolates: query heads are split into $g$ groups, each sharing one KV head, so $n_{kv} = g$ recovers MHA quality at $g=h$ and MQA speed at $g=1$; Ainslie et al. show that uptraining an existing multi-head checkpoint to GQA-8 with only 5% of original pretraining compute nearly closes the quality gap to full MHA while matching MQA's latency [@ainslie-2023-gqa]. GQA is now the default in essentially every recent open-weight dense model: Llama 3.1 8B/70B/405B all use 8 KV heads regardless of total head count (32/64/128) [@meta-2024-llama3], and the same pattern recurs in Mistral, Qwen, Gemma and gpt-oss below. The mechanism is trivial to retrofit into any serving engine's paged-attention and FlashAttention kernels, since a GQA layer is still "one KV cache slab per layer," only narrower.

### Compressing instead of pruning: multi-head latent attention

DeepSeek-V2 took a different route: rather than sharing raw keys/values across heads, multi-head latent attention (MLA) down-projects them into a shared low-rank latent $\mathbf{c}^{KV}_t \in \mathbb{R}^{d_c}$ per token per layer, plus a small decoupled RoPE key of dimension $d_h^R$ that cannot be folded into the latent because rotary position embeddings are not compatible with the up-projection trick; only these two pieces need to be cached, giving $L \cdot (d_c + d_h^R) \cdot s$ bytes/token with no factor of 2 [@deepseek-2024-mla]. With $d_c = 4d_h$ and $d_h^R = d_h/2$, DeepSeek's own comparison table states this is "equal to GQA with only 2.25 groups" while matching or exceeding vanilla MHA quality, and reports a 93.3% KV cache reduction and 5.76× higher throughput relative to their own prior 67B dense model [@deepseek-2024-mla] – vendor-reported, against DeepSeek's own baseline, not an independent benchmark. DeepSeek-V3 keeps the same design at larger scale ($d_c=512$, $d_h^R=64$, $L=61$) [@deepseek-2024-v3]. DeepSeek-V3.2-Exp (September 2025) and DeepSeek-V3.2 (December 2025) add DeepSeek Sparse Attention (DSA) on top of the same MLA cache: a "lightning indexer" scores preceding tokens and a selector restricts attention to the top-2048 cached latents per query, cutting per-layer attention compute from $O(n^2)$ to $O(nk)$ (where $n$ is sequence length and $k=2048$) without shrinking the cache itself [@deepseek-2025-v32exp; @deepseek-2025-v32]. DeepSeek-V3.2-Exp's own release notes describe it as "an intermediate step toward our next-generation architecture" [@deepseek-2025-v32exp]; the subsequent DeepSeek-V3.2 report (December 2025) does not repeat this framing, presenting itself instead as narrowing the gap with GPT-5 and Gemini-3.0-Pro on reasoning and agentic benchmarks, and its own conclusion lists specific remaining limitations relative to Gemini-3.0-Pro (narrower world knowledge from fewer training FLOPs, lower token efficiency, weaker performance on the hardest tasks) rather than framing V3.2 itself as transitional [@deepseek-2025-v32]. As of September 2026 DeepSeek has not published a model it calls "V4." V3.2's sparse-attention kernels (a separate indexer cache, a paged layout tuned to block size 64) needed day-0 engineering work in vLLM before serving efficiently [@vllm-2025-dsa].

### Bounding the window: sliding and local/global interleaving

Mistral 7B pairs GQA (8 KV heads) with sliding-window attention (SWA): each layer attends only to the last $W=4096$ tokens in a fixed-size rotating buffer, while stacked layers still propagate information roughly $W \times L$ tokens back [@jiang-2023-mistral7b]. Because every layer is capped, the cache stops growing once the sequence exceeds $W$. Gemma 2 interleaves one sliding-window layer ($W=4096$) with one full-attention layer ($1{:}1$) [@google-2024-gemma2]; Gemma 3 pushes this to $5{:}1$ with $W=1024$ to control KV memory at its 128K context [@google-2025-gemma3]. In a separate 2B-parameter, text-only ablation using a different ($1{:}3$) local:global ratio at the same window size, the authors report that KV-cache memory overhead at a 32K-token context falls from 60% (global-only baseline) to under 15% – evidence for the mechanism, but not a measurement of the shipped $5{:}1$, 27B-scale configuration [@google-2025-gemma3]. gpt-oss goes further, alternating a $W=128$ banded window with full attention every other layer, with only 8 KV heads for 64 query heads (group size 8) [@openai-2025-gptoss]. The trend (4096 → 1024 → 128) shows vendors trusting the global layers, not the local ones, for long-range recall, but none of these model cards publish an ablation isolating the accuracy cost of window size alone – treat the smallest windows as a compute/memory bet, not a proven-lossless one.

### Sharing keys and values across layers: CLA and YOCO

A layer-orthogonal idea is to stop assuming every layer needs its own KV projection. Cross-Layer Attention (CLA) shares KV activations between adjacent layers ("sharing factor" 2, 3, ...); combined with MQA, CLA2 gives another 2× cache reduction with under 1% perplexity change in 1B–3B-parameter experiments, a Pareto improvement over shrinking head dimension instead [@brandon-2024-cla]. YOCO goes further: a "self-decoder" (the first $L/2$ layers, efficient attention) produces one global KV cache that every layer in the second-half "cross-decoder" reuses via cross-attention, so memory scales as $O(N + CL)$ instead of $O(NL)$; the authors report roughly 80× less KV memory at 65B scale and 2.87–71.8× faster prefill (from early-exiting before the cross-decoder), scaling to a 1M-token context [@sun-2024-yoco]. Neither technique has, as of September 2026, shipped in a frontier open-weight production model at the scale GQA and MLA have – CLA's experiments stop at 3B parameters, YOCO's largest reported model is 13B – so generalization to 100B+ MoE models remains unverified rather than disproven.

### Replacing most layers' attention with recurrence

The most aggressive reduction discards per-token KV storage in most layers entirely. Jamba interleaves Transformer attention layers with Mamba (state-space) layers at roughly 1 attention layer per 8 total (its released 32-layer config keeps only 4), giving an 8× smaller KV cache than an equivalent all-attention model by the authors' own accounting – reproduced exactly by $32/4 = 8$ [@lieber-2024-jamba]. Qwen3-Next-80B-A3B mixes Gated DeltaNet (linear attention, a fixed-size recurrent state) with full GQA attention at 3:1 (36 linear layers to 12 attention layers) [@alibaba-2025-qwen3next]. Kimi Linear hybridizes its own Kimi Delta Attention (KDA, a fine-grained-gated refinement of Gated DeltaNet) with full MLA layers at the same 3:1 ratio, reporting up to 75% less KV cache and 6× faster decoding at 1M-token context versus a matched full-MLA baseline [@kimiteam-2025-linear]. MiniMax-01 places one softmax/GQA layer after every seven lightning-attention (linear) layers, motivated by their own finding that pure lightning attention has "limited retrieval capabilities" alone [@minimax-2025-01]. NVIDIA's Nemotron-H keeps only about 8% of layers as self-attention (10 of 118 in the 56B model, 4 of 52 in the 8B model), the rest split between Mamba-2 and FFN layers; the authors report up to 3× higher inference throughput than similarly-sized all-attention models (Qwen2.5, Llama-3.1) on NVIDIA H100 GPUs at a 65,536-token input / 1,024-token output setting – vendor-reported, at one specific sequence-length/hardware point, not shown to generalize across other context lengths or accelerators [@nvidia-2025-nemotronh]. In each design the non-attention layers carry a *fixed-size* recurrent state, independent of context length, so total cache memory eventually comes to be dominated by the handful of retained attention layers alone.

### Trade-offs: quality, kernels, and paging/prefix-cache compatibility

GQA is the safe default: near-lossless when trained from scratch, cheaply retrofittable by uptraining, and supported natively by every mainstream serving engine's paged-attention and FlashAttention kernels, since a GQA cache is just a narrower version of the same per-layer tensor. MLA buys a larger reduction but is a from-scratch architectural commitment, not a drop-in conversion: its "absorb $W^{UK}$ into $W^Q$" inference-time trick changes matmul shapes enough that dedicated kernels (FlashMLA, custom decode paths in vLLM/SGLang/TensorRT-LLM) were needed before it served efficiently; DSA on top of it required a second indexer cache and new paged-block layouts, a non-trivial integration exercise even for engineers with full access to the reference implementation [@vllm-2025-dsa]. Sliding-window layers are well supported by windowed FlashAttention/xFormers kernels, but mixing attention types in one model requires a "hybrid KV cache manager" that allocates different physical memory per layer type rather than one uniform block size; vLLM's own account of adding Qwen3-Next support describes building exactly such a manager, alongside Triton kernels ported from the Flash Linear Attention project, to keep linear-attention and full-attention layers from fragmenting the same paged pool [@vllm-2025-qwen3next]. CLA and YOCO remain comparatively kernel- and framework-immature: their layer-sharing patterns are not yet first-class citizens in major engines' paging logic the way GQA and (increasingly) MLA are. Hybrid SSM/linear-attention models were the hardest case for prefix caching specifically: PagedAttention-style block reuse and radix-tree caches assume a cache that decomposes into independent, copyable per-token blocks, which holds for GQA, MQA, MLA, CLA and, within their window, sliding-window layers; a Mamba or gated-DeltaNet recurrent state is instead a single fused summary that cannot be split the same way, so a shared prompt prefix cannot simply have its state copied into a new request. As of September 2026 this has moved from unsolved to merely unfinished: vLLM has merged automatic prefix caching for Mamba1, Mamba2, ShortConv and Gated DeltaNet hybrid layers by checkpointing recurrent state at aligned block boundaries and resuming computation on a cache hit [@vllm-2025-hybridapc], and a first-party engineering write-up describes the Mamba-2 case as functional but "in an experimental state" as of November 2025 [@ibm-2025-hybridvllm]. It ships opt-in rather than as the default, behind a `--mamba-cache-mode` flag, and – per the same tracking issue – making it the default, competitive in decode-heavy workloads, and compatible with speculative decoding remained open work as of September 2026 [@vllm-2025-hybridapc]; this is now a narrower problem of production hardening than of basic feasibility, unlike pure-attention models, where PagedAttention-style prefix caching is already the standard, on-by-default behavior of major serving engines (the subject of the next section). None of this makes the techniques mutually exclusive – MLA, sliding windows and hybrid recurrence are each usually paired with GQA in their remaining full-attention layers, so in practice they stack rather than compete.

## Compressing and Evicting the Cache

Paging and 8-bit KV quantization defer, but do not solve, GPU memory pressure: at million-token contexts or large batch sizes even an 8-bit cache can exceed HBM. Two further strategies push past this ceiling: shrinking each cached element below one byte, or discarding most cached tokens and keeping only the ones a future query needs, either permanently (eviction) or transiently, re-selected at every step (sparse retrieval). Both trade quality for memory and bandwidth, and the size of that trade — not the headline ratio — is what this section examines.

### Sub-byte quantization: FP8, FP4, and learned codebooks

FP8 KV caches (vLLM, TensorRT-LLM) are a supported option on Hopper- and Blackwell-class GPUs — enabled explicitly (e.g. vLLM's `kv_cache_dtype="fp8"`; the default is otherwise the model's native dtype, and, as of late 2025, vLLM defaults to FP8 automatically only for specific architectures such as DeepSeek-V3.2) — halving KV memory versus bf16/fp16 [@vllm-fp8]. Blackwell extends this to 4-bit floats: MXFP4 shares one power-of-two scale per 32-value block, while NVFP4 shares a higher-precision FP8 scale per 16-value block, giving lower quantization error on larger models [@nvidia-2025-nvfp4]. In a December 2025 Blackwell benchmark, NVIDIA reports NVFP4 KV cache halving memory versus FP8 KV, doubling the effective context/batch budget, and staying under 1% accuracy change on LiveCodeBench, MMLU-Pro, MBPP, and RULER-64K; on Llama 3.3 70B, NVFP4 scores roughly 5 points higher than MXFP4 at the same width (vendor-reported, single model) [@alvarez-2025-nvfp4kv]. 4-bit values must still be dequantized to FP8 before the attention matmul, so the compute saving is smaller than the memory saving.

Academic work pushes below 4 bits with data-dependent codebooks. KVQuant quantizes keys per-channel and *before* RoPE (which otherwise mixes channels of different magnitude), uses non-uniform, per-layer sensitivity-weighted levels, and stores the top ~1% of outliers per vector at higher precision, holding perplexity degradation under 0.1 on WikiText-2/C4 at 3 bits (4.8× vs fp16) across the LLaMA and Mistral families, and letting a LLaMA-7B model serve 1M tokens on one 80 GB A100 at 2 bits, or 10M tokens on 8 GPUs [@hooper-2024-kvquant]. At 128K tokens the authors report LLaMA-7B's cache falling from 64 GB (fp16) to 16/12/8 GB at 4/3/2 bits — 8× at the most aggressive setting, since the outlier overhead is small [@hooper-2024-kvquant]. QServe couples 4-bit KV quantization to the rest of the stack (4-bit weights, 8-bit activations, 4-bit KV), with a "SmoothAttention" transform shifting quantization difficulty to the unquantized queries; it reports end-to-end throughput 1.2×–1.4× (Llama-3-8B) and 2.4×–3.5× (Qwen1.5-72B) over TensorRT-LLM on A100/L40S, with L40S under QServe matching or exceeding A100 under TensorRT-LLM (self-reported) [@lin-2024-qserve]. KIVI's tuning-free 2-bit scheme (per-channel keys, per-token values), discussed earlier, remains a useful floor case: like KVQuant it shrinks every token rather than discarding any, so it degrades gracefully as the ratio tightens [@kivi].

### Deciding what to keep: eviction and retention

A different family drops tokens to hold a fixed budget independent of length. StreamingLLM finds that a handful of initial tokens — "attention sinks" — absorb outsized attention regardless of content; a sliding window that drops them collapses in perplexity once full, but keeping four sink tokens plus a recent window restores stability to 4M+ tokens without fine-tuning, at up to 22.2× lower latency than recomputing a window from scratch [@xiao-2023-streamingllm]. The caveat: this restores *fluency*, not *recall* — content outside the sink-plus-window is gone, not approximated, so the method suits open-ended streaming better than tasks that must recall arbitrary earlier context.

H2O scores tokens by accumulated attention weight and splits a budget between these "heavy hitters" and recent tokens, framed as dynamic submodular maximization with an approximation bound. At a 20% budget it reports up to 5× KV memory reduction with no accuracy loss across OPT/LLaMA/GPT-NeoX (6.7B–175B) on HELM and lm-eval-harness, and up to 29× higher throughput than DeepSpeed Zero-Inference or Accelerate [@zhang-2023-h2o]. SnapKV instead treats the *end of the prompt* as an observation window, keeping only the prior tokens each head consistently attends to from it; fine-tuning-free, it reports 3.6× faster decoding and 8.2× lower memory at 16K tokens, with only a small NIAH drop out to 380K tokens [@li-2024-snapkv]. Its authors note the limit directly: it compresses the *generation-phase* cache after the prompt is processed, so it cannot extend a model's long-context ability nor cut prefill cost [@li-2024-snapkv].

PyramidKV varies SnapKV's per-head budget *by layer*, following an observed "pyramidal" pattern where attention is diffuse low and concentrated high. On LongBench it matches full-cache accuracy at a 12% budget, and at an extreme 0.7% beats StreamingLLM, H2O, and SnapKV by up to 20.5 points on TREC; on NIAH, 128 entries per layer let LLaMA-3-70B match full-cache accuracy exactly [@cai-2024-pyramidkv]. Ada-KV targets a separate inefficiency: all of the above split a budget *evenly* across heads despite heads varying sharply in attention concentration. It reallocates a shared budget across heads by minimizing a derived eviction-loss bound, plugs into SnapKV or PyramidKV at no added memory cost, and reports gains over uniform allocation across 13 RULER and 16 LongBench datasets — widest question-agnostically, where SnapKV's observation-window trick is least reliable [@feng-2024-adakv].

### Retrieval-preserving sparsity: Quest and trainable sparse attention

Eviction carries a structural risk: a token dropped because it looked unimportant for one query may be exactly what a later, different query needs. Quest avoids this by discarding nothing: it keeps the full paged cache but at each step scores per-page key summaries against the *current* query to bound each page's attention weight, then attends only to the top-K pages — since the query changes every step, so does the selection. It reports up to 7.03× self-attention speedup and 2.23× end-to-end latency reduction at 32K context with negligible loss on PG19 perplexity, passkey retrieval, and LongBench [@tang-2024-quest]. For a cache of $L$ tokens in pages of size $S$ with $K$ pages selected, Quest loads roughly $1/S + KS/L$ of the cache per step — small when $K \ll L/S$, but this cuts *bandwidth and compute*, not resident memory: the full cache still has to be stored.

DeepSeek's Native Sparse Attention (NSA) makes the selection pattern *trainable*. A 27B-parameter MoE model with NSA, pretrained on 270B tokens and context-extended to 32K via YaRN, combines compressed coarse blocks, selected fine blocks, and a local window behind hardware-aligned kernels, matching or exceeding a dense baseline on general, long-context, and reasoning benchmarks, with up to 9.0×/6.0× forward/backward speedup over FlashAttention-2 at 64K — at research scale [@yuan-2025-nsa]. Its production successor, DeepSeek Sparse Attention (DSA), shipped in the 685B-parameter DeepSeek-V3.2-Exp model released 2025-09-29: a small "lightning indexer" scores each query against every prior key and selects a top-$k$ (2048 default) subset for attention, cutting cost from $O(L^2)$ to $O(Lk)$ [@deepseek-2025-v32], with DeepSeek reporting "virtually identical model output quality" and benchmark performance "on par with" dense DeepSeek-V3.1-Terminus (self-reported, as of September 2025) [@deepseek-2025-v32exp]. Like Quest, DSA selects over an otherwise fully retained cache, so its gain is compute and latency, not stored bytes.

### What the benchmarks show, and where they mislead

Most methods above are validated on LongBench (21 English/Chinese long-document tasks: QA, summarization, few-shot, code, synthetic retrieval) [@bai-2024-longbench], RULER (needle-in-a-haystack variants plus multi-hop tracing and aggregation) [@hsieh-2024-ruler], and NIAH tests descending from Greg Kamradt's original single-fact probe [@kamradt-2023-niah]. RULER's own headline finding warns against reading too much into NIAH alone: models scoring near-perfectly on vanilla NIAH degrade sharply on RULER's harder categories well before their claimed context length, and only about half of the 17 models tested held acceptable accuracy at 32K [@hsieh-2024-ruler]. Since most compression papers report NIAH and/or LongBench, that warning applies to them too: passing NIAH is necessary but not sufficient, and a method's own paper is rarely its harshest test.

Two independent studies confirm this for compression specifically. A cross-method benchmark spanning quantization (FlexGen, KIVI), eviction (StreamingLLM, H2O), prompt compression (LLMLingua2), and KV-free architectures found quantization degrades gracefully and uniformly — it never discards a token outright — while other approaches are task-dependent: StreamingLLM and H2O hold near-perfect accuracy on code, hard prompt compression is weakest on the needle test since deleting the needle's surrounding text is fatal by construction, and middle-token retrieval (InfLLM) beats plain recency eviction (StreamingLLM) on NIAH; the study confines itself to "long input, short output" tasks, explicitly excluding multi-turn conversation and long generation as open problems [@yuan-2024-longctxbench].

Microsoft's SCBench fills that gap, testing methods across the full KV-cache lifecycle (generation, compression, retrieval, reloading) under multi-turn and multi-request reuse — the latter being prefix caching in production. Across sparse attention, eviction, KIVI quantization, and retrieval methods on six long-context LLMs, sub-linear-memory methods (most eviction/constant-budget approaches) perform reasonably single-turn but degrade substantially once reused across turns or requests, while $O(n)$-memory sparse attention (Quest-like, NSA/DSA-like) holds up better; query-conditioned methods such as SnapKV, which use the input's final segment to decide what to keep, specifically lose effectiveness in multi-request mode, where that segment differs across requests sharing a prefix [@li-2024-scbench].

Reasoning and long-generation workloads expose a third failure mode none of the above is built to catch, since all probe long *inputs* with short outputs. Chain-of-thought models take short prompts and produce very long, repetitive outputs — DeepSeek-R1-Distill-Llama-8B has been reported generating over 8× longer traces than a matched ground-truth answer on math benchmarks [@cai-2025-rkv]. Methods tuned for long-prompt compression do not automatically transfer: one evaluation found arithmetic-reasoning accuracy stable above roughly a 40% cache budget across several compression methods but falling sharply below ~20% — on the hardest configuration, from about 0.75 to under 0.5 — and, comparing model types at a 10% budget under matched compression, a DeepSeek-R1-distilled model held around 0.60 accuracy against roughly 0.5 for an instruction-tuned model of the same base that started from a higher (0.8) uncompressed accuracy [@liu-2025-shotkv]. Because reasoning traces are also unusually redundant, purpose-built methods can beat a full cache outright: R-KV, scoring redundancy alongside importance, matches full-cache math accuracy at a 10–34% budget and reaches 105% of it at 16% on one benchmark — the ceiling is not "how much can be discarded" but "how much of the trace is discardable regardless" [@cai-2025-rkv].

### Why eviction resists prefix sharing and storage offload

Prefix caching and offload both depend on KV *blocks* being immutable and shareable: identical prefixes across requests point to the same physical blocks (copy-on-write), and offloaded blocks move as opaque, contiguous units [@vllm-blog]. Eviction breaks both assumptions: a policy's surviving-token set is a function of the *specific request's* later content (H2O's attention scores, SnapKV/PyramidKV's observation window, Ada-KV's per-head reallocation), so two requests sharing a prefix generally retain a *different* subset of it once their queries diverge. Block-level sharing does not carry over — the system either caches the pre-eviction prefix and re-evicts per consumer, forfeiting the saving on shared prefixes, or caches several divergent post-eviction versions, forfeiting deduplication. Offload compounds this: moving a non-contiguous, request-specific set of surviving positions needs per-token provenance tracking rather than contiguous-block transfer, defeating the large sequential transfers that make offload bandwidth-efficient. SCBench's finding that constant-budget methods underperform specifically in multi-request (shared-prefix) mode, while $O(n)$-memory sparse attention holds up better, is the empirical signature of this mismatch [@li-2024-scbench]. Quantization sidesteps the problem: it changes *how* a token is stored, not *whether* it survives, so a quantized prefix remains the same token set as its fp16 original and block identity is preserved — at the cost of a footprint that, unlike eviction, still grows linearly with sequence length.

## Reusing the Cache Across Requests: Prefix Caching and Beyond

The preceding sections scope the KV cache to a single request. In practice, many requests to a deployment share large spans of identical tokens — a system prompt, tool schemas, a retrieved document, earlier conversation turns — and a system that recognizes the overlap can reuse the already-computed keys and values instead of recomputing them, so prefill work scales with tokens genuinely new to the request rather than its total length. Because prefill is compute-bound and dominates TTFT [@instinfer; @databricks], cross-request cache reuse acts directly on TTFT rather than TPOT, and is now the primary latency and cost lever in agentic and multi-turn deployments, where most tokens sent on a given turn were already sent on the previous one.

### Automatic prefix caching: hash-based blocks and radix trees

vLLM's Automatic Prefix Caching (APC), building on the block-based KV cache allocator (PagedAttention) introduced above, partitions the KV cache into fixed-size blocks and hashes each block from its own tokens plus the previous block's hash, so a block's identity encodes its full prefix [@vllm-prefix-design]. A new prompt is hashed block by block against a hash-keyed pool; matched blocks are pinned against eviction, and LRU reclaims the rest, evicting a request's last (least reusable) block first. As of v0.11 vLLM defaults to collision-resistant SHA-256, and an optional `cache_salt` isolates reuse per tenant, closing a timing side-channel by which one tenant could otherwise infer another's cached content from latency alone [@vllm-prefix-design]. vLLM is explicit about the limit: APC "does not reduce the time of generating new tokens," so it helps only prefill and gives nothing when a request shares no prefix with prior traffic or the response is long relative to the prompt [@vllm-2025-apc].

SGLang's RadixAttention keeps the KV cache of all recent requests live in a radix tree instead of freeing it at completion, evicting leaves first so shared ancestors persist [@zheng-2024-sglang]. It defines hit rate as cached-prompt-tokens / total-prompt-tokens, and proves (Theorem 3.1) that scheduling by longest-matched-prefix-first equals a depth-first radix-tree traversal and achieves an optimal cache hit rate once the cache holds at least the longest request — the basis of its cache-aware scheduler. The paper proves this for hit rate specifically, not throughput directly; a higher hit rate plausibly helps throughput, but that link is not what Theorem 3.1 establishes, and the online case only approximates the DFS order the proof relies on. Across agent, few-shot, RAG and multi-turn chat workloads, SGLang reports up to 6.4$\times$ higher throughput than contemporary systems, with first-token latency the biggest beneficiary [@zheng-2024-sglang]. Mooncake's cluster scheduler (Conductor) extends this across machines, estimating TTFT per candidate prefill node from request length and that node's prefix-match length, and routing to whichever minimizes predicted TTFT rather than balancing on queue length alone [@qin-2025-mooncake].

### Beyond exact prefixes: non-prefix and position-independent reuse

Hash- and radix-based caching only helps when shared text is a byte-identical *prefix*. RAG breaks this: reused chunks rarely start the prompt, and one differing token earlier invalidates every cached block after it, so prefix caching degrades toward full recompute once an input concatenates several independently-reused chunks [@yao-2025-cacheblend]. CacheBlend reuses precomputed KV for each chunk regardless of position and selectively recomputes a small, dynamically chosen subset of tokens per layer (empirically under 15%) to restore the cross-chunk attention naive splicing ignores; recompute for layer $L$ pipelines with loading layer $L{+}1$'s cached KV, adding negligible latency and letting cache live on slower, higher-capacity media without a TTFT penalty [@yao-2025-cacheblend]. EPIC's LegoLink uses a cheaper, static rule instead: it always recomputes only the first $k \le 32$ tokens of every non-initial chunk, enough to break the "attention sink" that otherwise corrupts accuracy under naive splicing, keeping recompute cost roughly linear in chunk count rather than quadratic in prompt length [@hu-2025-epic]. Both trade a small, bounded recompute for reuse patterns exact-prefix caching cannot exploit at all, so their headline numbers are not measured against a prefix-caching baseline: CacheBlend's are against full recompute, and EPIC's are against CacheBlend itself, the strongest prior position-independent-caching system. Both settings were chosen because prefix caching would show no benefit there in the first place, since none of the reused content sits at the prompt's start.

### Compressing the cache for network transfer: CacheGen

When a shared KV cache sits on a different machine than the consuming GPU — a disaggregated prefill/decode cluster, or a cache tier reached over ordinary datacenter networking rather than NVLink — fetching it competes with prefill itself for TTFT, since a KV cache commonly reaches tens of gigabytes while inter-server bandwidth is often single-digit Gbps [@liu-2024-cachegen]. CacheGen treats this as a streaming problem: it encodes KV tensors into compact bitstreams via quantization and arithmetic coding tuned to the cache's locality and per-layer sensitivity, decodes on GPU pipelined with transmission, and — like adaptive video bitrate — lowers per-chunk encoding level (or falls back to raw text for recomputation) as bandwidth drops, holding load time to an SLO [@liu-2024-cachegen]. Across four datasets and three models it cuts encoded KV size 3.5–4.3$\times$ versus a quantization-only baseline and total load delay 3.1–4.7$\times$ versus recomputing from text, with under 2% accuracy loss [@liu-2024-cachegen]. It complements the on-GPU quantization schemes discussed earlier (KIVI, LogQuant): those shrink the cache's resident footprint; CacheGen shrinks it for time in flight.

A worked example on Anthropic's multipliers: an 8,000-token stable prefix (system prompt plus tool schemas) reused over 10 turns costs $8{,}000\times\$2.50/10^6\approx\$0.020$ to write once, then $8{,}000\times\$0.20/10^6\approx\$0.0016$ per turn to read on each of the next 9 — about \$0.034 total, versus $10\times8{,}000\times\$2/10^6=\$0.16$ paying full price every turn: a 78.5% reduction on the shared portion, or a ~4.65$\times$ blended cost reduction [@anthropic-2026-promptcaching]. The compute-side effect is larger than this blended price ratio suggests, since engines skip the forward pass on a hit rather than merely discounting it [@vllm-2025-apc; @zheng-2024-sglang]: prefill FLOPs on turn 10 scale with only the newest ~200–400 tokens rather than the accumulated ~9,000, a ~23–45$\times$ compute reduction — well beyond the ~4.65$\times$ blended figure above, because that figure is diluted by the one-time write cost and turn 1's full-price miss, not by the 10$\times$ marginal discount that applies to cache reads alone. OpenAI states a matching asymmetry: caching can cut TTFT up to 80% on prompts above 10,000 tokens, more than the 90% price discount alone predicts, since removing computation also removes queuing on the prefill path [@openai-2026-cookbook].

### Why agentic and multi-turn workloads see very high hit rates

If a session resends a stable prefix of $P$ tokens (system prompt, tools, retrieved context) plus $\Delta$ new tokens per turn, hit rate at turn $t$ is $h(t)=\frac{P+(t-1)\Delta}{P+t\Delta}$: large already at $t=1$ when $P\gg\Delta$, and approaching $(t-1)/t \to 1$ as the session lengthens regardless of $P$ — exactly vLLM's two canonical APC cases, long-document Q&A (large constant $P$) and multi-round chat (growing, append-only history) [@vllm-2025-apc]. Anthropic's automatic-caching mode is built around this shape, moving the breakpoint forward each turn so only the newest turn is a write [@anthropic-2026-promptcaching]. Tool-calling agents are the extreme case — schema and instructions are large and static, each round-trip appends only a short call and result, so $\Delta\ll P$ by construction — consistent with Mooncake's production traces, already dominated by chat/agent sessions, sustaining hit rates near 50% once capacity was adequate [@qin-2025-mooncake].

This favorable case has limits. A hit needs an exact match to the breakpoint: reordering retrieved documents, inserting a timestamp early in the prompt, or randomizing few-shot order — all common in production RAG and eval harnesses — silently defeats hash/radix matching, the exact gap CacheBlend and EPIC target rather than a corner case [@yao-2025-cacheblend; @hu-2025-epic]. Hosted caches are scoped per tenant (OpenAI: not shared between organizations), so benefit is bounded by one tenant's repeat traffic, and Gemini's implicit mode gives no cost-saving guarantee even when a prefix repeats [@google-2026-contextcache]. The guaranteed 90%/75% split for Gemini's explicit cache (Table 4) is documented on Google Cloud's enterprise API surface rather than the Gemini Developer API cited elsewhere in this section; Gemini 2.0 models no longer appear on the Developer API's own current pricing or caching documentation as of September 2026, so that 75% figure is best read as an enterprise-specific or historical number rather than one confirmed on the consumer-facing API [@google-2026-vertexcaching]. Every technique here shortens prefill only — TPOT and output cost are unchanged — so workloads dominated by long generation rather than long, repeated prompts see smaller end-to-end gains [@vllm-2025-apc].

## Extending KV Cache Beyond GPU Memory (CPU Offloading & NVMe)

When the KV cache cannot fit in GPU VRAM – because of long sequences, large batches, or a small GPU – the cache (and sometimes the model weights) can be moved to host DRAM or to NVMe storage. This expands usable capacity by one to three orders of magnitude, but every tier below GPU HBM is reached over an interconnect that is both lower-bandwidth and, for storage, non-coherent, so offloading trades memory capacity for added latency and, in the worst case, a collapse in per-token throughput. The size of that penalty – and whether it is worth paying – depends on the specific interconnect, the access pattern (bulk sequential transfer vs. many small reads), and whether it would actually be cheaper to recompute the missing keys and values than to fetch them.

### Interconnect Bandwidth: PCIe, NVLink-C2C, and NVMe

The bandwidth available to move KV data off the GPU has roughly doubled with each of the last three PCIe generations, and on NVIDIA's Grace-based superchips it is now an order of magnitude higher than PCIe. **Table 2** gives the exact, per-direction figures.

Three corrections to how this bandwidth is usually discussed matter specifically for KV-cache offloading:

**PCIe is the default GPU$\leftrightarrow$host link.** A GPU on PCIe Gen4 x16 – the configuration used, for example, in InstInfer's own testbed [@instinfer] – can move KV data to and from host DRAM at about 31.5 GB/s in each direction; Gen5 roughly doubles this to 63 GB/s; Gen6 roughly doubles it again to about 128 GB/s per direction, per PCI-SIG's own bandwidth table [@pcisig-2021-pciebw], and was released to PCI-SIG members as a ratified specification in January 2022 [@pcisig-2022-ratified] – though commercial host platforms have followed the specification by several years. This is one to two orders of magnitude below GPU HBM bandwidth (~3 TB/s aggregate on an H100 SXM, as cited elsewhere in this whitepaper [@micron]) – the offload penalty discussed throughout this section is fundamentally this bandwidth gap, not a difference in kind.

**NVLink-C2C changes the calculus on Grace-based platforms.** NVIDIA's Grace Hopper (GH200) and Grace Blackwell (GB200/GB300) superchips connect the Grace CPU to its GPU with NVLink-C2C, a coherent interconnect delivering 900 GB/s of bidirectional bandwidth (450 GB/s per direction) – about 7× a PCIe Gen5 x16 link in each direction, and roughly 14× a Gen4 link [@nvidia-2022-gracehopper; @nvidia-2024-gb200]. On these platforms, CPU DRAM sits close enough to GPU speed that "CPU offload" is a materially different proposition than on a conventional PCIe-attached host: as of the shipping GH200 product specification, up to 480 GB of Grace LPDDR5X becomes addressable by the GPU, at up to 500 GB/s of CPU-side memory bandwidth [@nvidia-2024-gracedatasheet] – within a single order of magnitude of on-package HBM bandwidth, rather than two orders of magnitude below it. (NVIDIA's original November 2022 architecture blog described an earlier, pre-shipping configuration at up to 512 GB and 546 GB/s [@nvidia-2022-gracehopper]; the 480 GB/500 GB/s figures reflect the specification of the product as sold, current as of September 2026.) This does not eliminate the memory hierarchy – Grace's own LPDDR5X bandwidth and GPU HBM remain separate, lower ceilings that NVLink-C2C cannot exceed – but it substantially narrows the CPU tier's penalty relative to PCIe-only systems, and represents a genuinely different regime from the PCIe-bound conditions under which FlexGen, DeepSpeed's ZeRO-Inference, and InstInfer were built and measured.

**NVMe access latency is microseconds, not milliseconds; what constrains KV offload is bandwidth, not latency.** A representative contemporary enterprise NVMe SSD, the Micron 9400, reports a typical (queue-depth-1, 4 KB random) read latency of 69 $\mu s$ and write latency of 10 $\mu s$ [@micron-2024-9400ssd] – three to four orders of magnitude faster than the millisecond-scale figures sometimes assumed for disk. For KV-cache offload, where each fetch moves megabytes to gigabytes of contiguous key/value data rather than a single 4 KB block, per-request access latency is largely irrelevant; what determines fetch time is sustained bandwidth, which for a single drive's own external PCIe interface is on the order of 3–6 GB/s and up to 7 GB/s sequential read/write for current mainstream enterprise NVMe SSDs [@instinfer; @micron-2024-9400ssd]. Latency becomes a first-order concern only when the access pattern is many small, non-contiguous block reads issued at low queue depth – a real risk for block-based KV layouts (e.g., PagedAttention-style paging) that scatter a sequence's cache across many small pages rather than one contiguous region.

### Offloading to CPU Memory (RAM)

Two distinct DeepSpeed technologies are often conflated here, and the distinction matters for what follows. **ZeRO-Offload** [@ren-2021-zerooffload] is a *training*-time technique: it offloads optimizer states and gradients to CPU DRAM to fit larger models on a single GPU during training, and neither targets nor was evaluated on inference serving. The inference-time analogue is **ZeRO-Inference** [@deepspeed-2022-zeroinference], which instead pins model weights in CPU or NVMe memory and streams them layer-by-layer into the GPU during the forward pass, freeing GPU memory for a much larger batch size. A later DeepSpeed release extended ZeRO-Inference to also offload the *KV cache* itself to CPU memory, combined with 4-bit weight quantization; DeepSpeed reports up to a 20× throughput improvement over its own prior (non-KV-offloaded) release, a release-over-release headline figure distinct from the FlexGen comparison below [@deepspeed-2023-zeroinferkv]. In its own head-to-head comparison table (single A6000 GPU, 252 GB host memory, prompt length 512, generation length 32), this release reaches generation throughput at or above FlexGen's best CPU/NVMe-offload configuration on OPT-30B, OPT-66B, and OPT-175B – the three model sizes both frameworks support in that table – and separately reports results on BLOOM-176B and LLaMA-2-70B, for which FlexGen is marked "Unsupported," so no head-to-head figure exists for those two [@deepspeed-2023-zeroinferkv]. Hugging Face Accelerate offers comparable CPU- and disk-offload primitives for model weights, via its `device_map="auto"`, `cpu_offload()`, and `disk_offload()` mechanisms [@huggingface-2024-accelerate].

Once weights or KV cache are offloaded, the mechanism is the same regardless of which framework performs it: older key/value blocks are moved to host DRAM over PCIe (or NVLink-C2C, on Grace platforms) and brought back for attention. Because this happens on every decoding step for every offloaded token, the decode phase becomes bandwidth-bound on whichever interconnect is in use rather than bound by GPU compute – a point InstInfer's authors make explicitly, describing PCIe as "a new performance bottleneck" for this reason [@instinfer]. On a plain PCIe Gen4 x16 host this can reduce per-token throughput enough that CPU offloading beyond a small batch size becomes impractical for latency-sensitive serving; it is used almost exclusively in throughput-oriented, latency-tolerant settings (batch inference, benchmarking, offline scoring).

Mitigations fall into three categories: (1) **prefetching**, overlapping computation on the current token with the transfer of the next token's KV data, which hides some but not all of the latency, particularly at long sequence lengths where transfer volume dominates compute time [@moon-infinigen]; (2) **selective/quantized offload**, keeping a window of recent tokens on GPU and moving only older or less-attended tokens to CPU, optionally in compressed (8-bit or 4-bit) form to cut the bytes crossing PCIe [@moon-infinigen]; and (3) **importance-guided prefetch**, exemplified by InfiniGen, which runs a cheap approximate ("rehearsal") attention pass on CPU to identify which cached keys the next decoding step will actually need, then fetches only that subset from host memory rather than the full window – reported to improve the throughput of an offloading-based system by up to 3× over prior KV-cache management while also improving output quality relative to a fixed eviction policy [@infinigen; @moon-infinigen]. Head-wise offloading is a complementary, more recent direction: HeadInfer keeps only a subset of attention heads' KV cache on GPU at any time and computes the rest from CPU-resident data, reporting a reduction in on-GPU KV footprint for a 1-million-token sequence on Llama-3-8B from 128 GB to 1 GB (total GPU memory 207 GB to 17 GB), and separately demonstrating 4-million-token generation with an 8B model on a single 24 GB consumer GPU (e.g., an RTX 4090) [@headinfer]. All of these techniques reduce *how much* must be fetched or *when* it is fetched; none of them raises the underlying interconnect bandwidth, so they compose with, rather than replace, the choice of link discussed above.

### Offloading to SSD/NVMe (Persistent Storage)

When even CPU DRAM is insufficient – or when the goal is minimizing hardware cost for throughput-oriented batch inference rather than minimizing latency – KV cache (and weights) can be spilled to NVMe. **FlexGen** is the reference system here [@flexgen]. Running OPT-175B on a single 16 GB NVIDIA T4 GPU with 208 GB of CPU DRAM and 1.5 TB of SSD, FlexGen reached, for the first time, a sustained generation throughput of 1 token/s using an effective batch size of 144 with 4-bit weight and KV-cache compression. Its own reported comparisons are precise and worth stating exactly, because the widely repeated "100×" figure is easy to misstate: at a batch latency of about 4,000 seconds (roughly 67 minutes to complete the whole batch, not per token), FlexGen's 4-bit configuration reached 100× higher maximum throughput than the contemporaneous CPU/disk-offloading baselines it compared against – DeepSpeed's (pre-KV-offload) ZeRO-Inference and Hugging Face Accelerate – which were limited to a batch size of 2 by out-of-memory errors at that point on the latency-throughput curve; without compression, FlexGen reached 69× at a batch latency of about 12,000 seconds (200 minutes) [@flexgen]. The comparison is against prior *offloading* systems on the same single-GPU hardware, not against GPU-only serving, which cannot run OPT-175B at all on a 16 GB GPU without offloading, model parallelism, or heavy compression. The throughput gain also comes bundled with the latency cost: these are batch-completion times measured in thousands of seconds, and FlexGen is explicitly designed for latency-insensitive, throughput-oriented workloads, not interactive serving.

InstInfer's and DeepSpeed's own benchmarks probe the same phenomenon at smaller scale, and let us see precisely where FlexGen (and CPU-only offload) breaks down. InstInfer's authors evaluated OPT-13B, FP16, input/output length 1024, on a single 48 GB A6000 GPU (Gen4 PCIe host, ~32 GB/s to CPU): DeepSpeed's host-memory-only offload outperforms the other dense (non-InstInfer) schemes at small batch sizes (4–16), where the cache still fits in host memory, but degrades sharply – by 32.6× relative to batch size 16 – once it must additionally spill from host memory to SSD at batch size 32; FlexGen's SSD-offload mode holds up to batch size 64, and hits an outright out-of-memory error at batch size 128, because the *intermediate* KV cache generated during prefill (not just the steady-state cache) exceeds available VRAM [@instinfer]. A latency breakdown at these settings shows the bottleneck shifting with batch size: at small batches (4–8), where the KV cache still fits on GPU, most decode time is spent on weight access; once the KV cache must be offloaded, KV-cache access alone accounts for up to 98.9% of decode latency [@instinfer].

InstInfer's proposed fix is to move computation to the data rather than the reverse: a Computational Storage Drive (CSD) – an NVMe SSD with an on-board FPGA – performs the decode-phase attention computation itself, next to the flash, and returns only the much smaller attention output to the GPU over a direct peer-to-peer DMA path that bypasses the host [@instinfer]. Their testbed CSD is a Xilinx Zynq7045 FPGA-based prototype whose flash-channel bandwidth (8 channels $\times$ 1.4 GB/s) was configured to match a Samsung 980 Pro's aggregate throughput, paired with an actual Samsung 980 Pro (2 TB) for storage capacity, on a Gen4 PCIe host [@instinfer] – not a literal 980 Pro with an embedded FPGA. The CSD's realized internal bandwidth was about 11.2 GB/s – higher than a typical NVMe drive's own external PCIe interface bandwidth (3–6 GB/s, since most drives use a Gen4 x4 link) but still below the ~32 GB/s Gen4 x16 GPU$\leftrightarrow$host link in their setup.

The headline 11.1× and the more conservative 6.85× are not the same comparison, and conflating them overstates what in-storage computation alone achieves. InstInfer's own evaluation reports 6.85× over FlexGen with dense (non-compressed) in-storage attention at the *same* batch size, 64 – the largest batch FlexGen itself can reach (it runs out of GPU memory for the intermediate prefill-phase KV cache at batch size 128). The 11.1× figure is dense in-storage attention *plus* an additional sparse-attention KV-compression scheme (SparF, 1/8 compression ratio), run at batch size 256 – a batch size FlexGen cannot reach at all – compared against FlexGen's own maximum (at batch size 64) [@instinfer]. InstInfer's authors separately isolate SparF's own contribution, holding batch size fixed at 256: SparF improves throughput by 2.08× over dense in-storage attention at that same batch size [@instinfer]. Combining the two reported multipliers ($11.1 / 2.08 \approx 5.3$) implies dense in-storage attention alone reaches roughly 5.3× FlexGen's maximum at batch size 256 – a number the paper does not state directly, but which shows that part of the 6.85×$\to$11.1× gap reflects InstInfer's architecture supporting a batch size FlexGen cannot reach, on top of (not only) the compression from SparF. This is one instance of a broader pattern (also visible in InfiniGen and HeadInfer above): offload-side systems research has moved from "move the bytes faster" toward "move fewer bytes, and move the computation instead." All of these results, however, are reported for a specific model size (13B), hardware pairing (A6000 plus a single consumer NVMe drive), and workload (1024-token sequences); none of the cited papers demonstrates that the reported multipliers hold for substantially larger models, multi-drive storage arrays, or online (rather than offline/batch) serving, where tail latency rather than aggregate throughput is the binding constraint.

The move to faster NVMe also matters directly, independent of any algorithmic change. DeepSpeed's 2025 benchmarks of ZeRO-Inference on LLaMA-3-70B (single GPU, prompt length 512, generation length 32, batch size 96, using NVIDIA GPUDirect Storage to move data directly between NVMe and GPU memory) report generation throughput rising with available NVMe bandwidth: 7 tokens/s with four PCIe Gen4 NVMe drives on an Azure NC\_A100\_v4 (A100-class) VM, and 17 tokens/s with four Gen5 drives, rising to 26 tokens/s with eight Gen5 drives, both measured on an Azure ND-H200-v5 (H200-class) VM [@deepspeed-2025-deepnvme]. Because the GPU generation changes alongside the NVMe generation between the Gen4 baseline and the Gen5 comparison points, this is suggestive of the bandwidth-bound framing above rather than a clean, single-variable demonstration of it: a newer, faster GPU can also relieve other parts of the pipeline (e.g., the PCIe/host-to-GPU transfer itself, or on-GPU compute), so some of the 7$\to$17 tokens/s jump cannot be attributed to NVMe bandwidth alone. The 17$\to$26 tokens/s step, by contrast, holds the GPU generation fixed (both on ND-H200-v5) and varies only drive count, so it is a cleaner within-generation demonstration of the bandwidth-bound claim.

### Recompute vs. Reload: A Worked Trade-off

Offloading assumes that fetching cached keys and values is cheaper than recomputing them through prefill. That is not automatic: it depends on the ratio of KV-cache bytes to be fetched (which scales with sequence length and model width) against the FLOPs required to recompute them (which scales with sequence length and total model size), relative to the available compute throughput and the bandwidth of whichever tier holds the cache. Cake, an ICML 2025 system built specifically around this trade-off, frames the decision using representative bandwidth/capacity figures for a single-node GPU server: roughly 2 TB/s and 80 GB for GPU memory, roughly 25 GB/s and 1.8 TB for CPU memory, and 0.5–4 GB/s and 26 TB for local/remote disk [@jin-2025-cake]. Because disk capacity so far exceeds GPU and CPU memory, the same paper cites an earlier system, AttentionStore, which found that roughly 80% of KV-cache hits in a multi-turn-conversation workload land on the slowest, disk tier [@gao-2024-attentionstore; @jin-2025-cake] – exactly the regime in which the recompute-vs-load choice is least obvious.

The following illustrative calculation (assumptions stated; not a benchmark) makes the trade-off concrete for a 13B-class dense model with the published Llama-2-13B architecture – 40 layers, 5120-dimensional hidden state, no grouped-query attention [@nvidia-2025-nemollama2] – reusing a $T=2048$-token cached prefix:

- **KV-cache volume.** FP16 KV bytes per token $= 2~(\text{K, V}) \times L \times d_{model} \times 2~\text{bytes} = 2 \times 40 \times 5120 \times 2 = 819{,}200$ bytes $\approx 0.82$ MB/token. For $T=2048$ tokens: $819{,}200 \times 2048 \approx 1.68$ GB (using the exact per-token byte count; rounding to "0.8 MB/token" first, as some published treatments do, understates the total by about 2%, giving 1.64 GB instead).
- **Recompute cost.** Prefill FLOPs $\approx 2 \times P \times T = 2 \times 13\times10^{9} \times 2048 \approx 5.3\times10^{13}$ FLOPs (the linear, matmul-dominated approximation; at this length the quadratic self-attention term is still sub-dominant, but it will not stay that way as $T$ grows – see below). On an RTX A6000 (154.8 TFLOPS dense FP16 tensor peak – derived by halving NVIDIA's published 309.7 TFLOPS sparse figure per the standard Ampere 2:1 structural-sparsity convention, since the datasheet does not itself print a dense figure [@nvidia-2021-a6000]) at an assumed, deliberately conservative 50% of peak utilization ($\approx 77$ TFLOPS effective), recompute takes $5.3\times10^{13}/7.7\times10^{13} \approx 0.69$ s.

| Source tier | Bandwidth | Time to load 1.68 GB |
| --- | ---: | ---: |
| NVLink-C2C (Grace Hopper/Blackwell) | 450 GB/s | ~3.7 ms |

At this model size and sequence length, reloading from any *local* tier – CPU DRAM over any PCIe generation, NVLink-C2C, or a local NVMe drive – is cheaper than recomputing, by a factor of roughly 2.7× (single NVMe drive) to roughly 185× (NVLink-C2C). The trade-off flips toward recompute only once the cache must come over a slow, oversubscribed, or congested remote link; a plain 10 GbE path (1.25 GB/s) is already slower than recompute in this example. This matches the design premise of Mooncake's disaggregated KVCache pool, which relies on a well-provisioned RDMA fabric (up to 8×400 Gbps between nodes) specifically so that loading remains cheaper than recomputing even when the cache lives on a remote node's CPU/DRAM/SSD rather than locally [@qin-2025-mooncake].

Three caveats keep this from being a general rule. First, the crossover point moves with model size and sequence length: KV bytes per token scale roughly with $d_{model}$ (linear in model width), while recompute FLOPs per token scale with total parameter count $P$, which grows faster than $d_{model}$ across a model family (roughly $P \propto L \times d_{model}^2$ for fixed head dimension) – so larger models shift the balance further toward loading, and the quadratic growth of the self-attention term with $T$ eventually makes recompute relatively more expensive at very long context lengths as well, pushing in the same direction. Second, this calculation ignores contention: a production server holds many concurrent requests sharing the same PCIe/NVMe links and the same GPU compute, so the *effective* per-request bandwidth and FLOPs are both lower than the peak figures used here, and recomputing also consumes GPU cycles that could otherwise serve other requests' decode steps – precisely the resource-contention problem Cake's scheduler is built to manage, by running recompute and reload for different chunks of the same request in parallel rather than treating them as a binary choice [@jin-2025-cake]. Third, none of the bandwidths above account for fixed per-request overhead (kernel launch, page-table lookups for non-contiguous block-based layouts) that can matter when the cached region is small or fragmented.

### System Design Considerations

The pattern across InfiniGen, HeadInfer, InstInfer, Cake, and Mooncake is convergent: newer systems minimize *how much* KV data crosses the slow link, move computation to where the data already sits (in-storage attention, head-wise offload), or overlap reload with recompute rather than treating interconnect bandwidth as fixed and unavoidable. None of this makes the underlying bandwidth gap disappear – it remains the reason CPU/NVMe offload is a throughput-for-latency trade rather than a free capacity increase – but it does mean that a flat bytes-over-bandwidth estimate, without accounting for compression, selective fetching, or near-data compute, will systematically overstate the real cost of offloading in a well-engineered system.

One further point is worth making explicitly, since speculative decoding is sometimes described as a fix for offload latency: it is not. Speculative decoding [@leviathan; @chen-spec] reduces the number of full forward passes of the *large* model required to produce a given number of output tokens, by having a small draft model propose several tokens that the large model then verifies in one batched pass. Whether that helps an offloaded deployment depends entirely on whether the KV-cache fetch needed for the verification pass can be amortized across the $k$ draft tokens in a single, larger transfer, rather than issued as one small transfer per token; if the serving stack still fetches KV data per generated token regardless of how those tokens were produced, speculative decoding changes nothing about the I/O bottleneck – it only reduces large-model compute, which is a separate axis from the memory-bandwidth constraint this section addresses. It is also not free: the draft model itself requires compute (and, for long contexts, its own KV cache), and an acceptance rate below 100% means some of that compute is wasted. Production stacks such as ByteDance's Doubao-1.5-pro do pair speculative decoding with decode-oriented hardware to cut TPOT [@doubao15], but that source describes a general low-cost-decode strategy, not an offload-latency-masking mechanism specifically, and no such mechanism is claimed here.

## Disaggregated Serving and KV Transport

The preceding sections treated the KV cache as something to keep close to the compute that consumes it — on-GPU, then CPU, then SSD. An orthogonal strategy, now common in large production deployments, keeps the cache in GPU memory throughout but moves it *between* GPUs: the prefill phase (compute-bound, prompt-parallel) and the decode phase (memory-bandwidth-bound, autoregressive) run on separate machines, and only the resulting KV cache — not the prompt or the model — crosses the network. (Some production stacks instead ship intermediate per-layer activations across this same boundary rather than a finished KV cache — a related but distinct transfer profile this section does not size.) This section surveys the systems that implement this "disaggregated" or "P/D-split" architecture and works through the bandwidth it demands.

### Why separate the phases

DistServe and Splitwise established the case independently. Colocating prefill and decode in one continuous-batching engine forces a scheduler to interleave a compute-bound burst (prefill) with an ongoing memory-bound stream (decode); the burst stalls in-flight decodes, inflating tail inter-token latency, and chunking the prefill only trades one tail cost for another [@distserve]. DistServe reports serving 7.4× more requests, or meeting 12.6× tighter SLOs, than a state-of-the-art colocated baseline at matched TTFT/TPOT targets and >90% SLO attainment, on A100 clusters [@distserve]. Splitwise's characterization of production Azure traces found token generation persistently under-utilizes GPU compute even at large batch sizes, so it dedicates separate "prompt pool" and "token pool" machines, reporting up to 1.4× higher throughput at 20% lower cost, or 2.35× more throughput at matched power and cost, versus homogeneous non-split clusters [@splitwise]. Both papers make the transfer itself nearly free by overlapping it with computation: Splitwise streams each layer's KV block over InfiniBand as soon as that layer finishes rather than waiting for the whole prefill, measuring a non-overlapped transfer floor of about 5 ms on an H100 pair (400 Gb/s) and 8 ms on A100 (200 Gb/s) — under 7% of prefill time, on cloud InfiniBand links in the 25–50 GB/s-per-GPU-pair range [@splitwise].

### Production KVCache-centric systems

Moonshot AI's **Mooncake**, the serving platform behind the Kimi chatbot, pools the CPU, DRAM, SSD and RDMA-NIC resources of the *entire* GPU cluster into one disaggregated KVCache store, interconnected at up to 8×400 Gb/s per node, scheduling requests around where cache blocks already live rather than around GPU load alone [@qin-2025-mooncake]. Its Conductor scheduler reuses cached prefixes from remote nodes, streams newly computed KV to the decode node per-layer, and predicts overload to reject requests early rather than let them consume prefill compute they cannot finish decoding within SLO. On replayed production traces, Mooncake increases effective request capacity 59%–498% over baseline systems at matched TTFT/TBT SLOs; in Kimi's own fleet (over 100 billion tokens/day) it serves 115% more requests on A800 clusters and 107% more on H800 clusters than its predecessor (vendor-reported, production clusters) [@qin-2025-mooncake]. DeepSeek's own numbers show the same pattern at frontier MoE scale: DeepSeek-V3/R1 runs prefill (expert-parallel degree 32, four-node units) and decode (degree 144, eighteen-node units) as physically separate pools, reporting 73.7k input tokens/s and 14.8k output tokens/s per H800 node (8 GPUs) over a 24-hour production window (vendor-reported) [@deepseek-2025-inference].

### Platform- and engine-level support

**NVIDIA Dynamo** packages disaggregation as a first-class mode: a `PrefillRouter` selects a prefill worker by KV-overlap score or load, hands the request to a decode worker, and moves the KV cache with **NIXL**, NVIDIA's transport-agnostic library exposing one non-blocking, GPU-to-GPU point-to-point API over NVLink, InfiniBand/RoCE (via UCX), GPUDirect Storage or TCP [@nvidia-2026-dynamo; @nvidia-2025-nixl]. A separate KV-aware router tracks which blocks already live on which worker, so cache-hot requests can skip a remote prefill entirely. **llm-d** — a CNCF sandbox project founded by Red Hat, Google Cloud, IBM Research, CoreWeave and NVIDIA — layers the same idea onto Kubernetes: its Inference Gateway extension picks a prefill/decode pair per request and composes with prefix-cache-aware routing so only the *uncached* suffix of a prompt goes to a remote prefiller, over RDMA via NIXL or Mooncake's transfer engine (TCP is an explicit fallback marked "testing and development only") [@redhat-2025-llmd; @llmd-2026-disaggdocs]. Partner-reported benchmarks collected in the project (vendor-reported, individually sourced, not independently reproduced here) include a 70% output-throughput gain from P/D disaggregation on GPT-OSS/B200, and 10%–30% on GPT-OSS-120B/Llama-3.3-70B on AMD MI300X [@llmd-2026-repo].

At the engine level, both major open-source stacks expose disaggregation as a pluggable transport. vLLM's `KVTransferConfig` supports interchangeable connectors — `NixlConnector`, `MooncakeConnector`, `LMCacheConnectorV1`, a raw-NCCL `P2pNcclConnector` — but its own documentation states plainly that disaggregated prefill "does not improve throughput" by itself: the benefit is controlling tail inter-token latency and tuning TTFT independently of TPOT [@vllm-2026-disaggpf]. SGLang's `--disaggregation-mode {prefill,decode}` delegates transfer to Mooncake's engine or NIXL/UCX over RDMA; its GPU staging buffer for heterogeneous prefill/decode tensor-parallel sizes reports 2–5× higher transfer throughput than naive per-token slicing [@sglang-2026-pd]. On AMD MI300X with the Mooncake backend, one prefill/one decode instance reports 2.2×–6.9× more SLO-compliant *goodput* than a collocated server, the larger gain on the longer-prompt (3,200-in/800-out) workload versus heavy-decode (1,024-in/2,048-out) (vendor-reported, AMD ROCm blog) [@amd-2025-rocmsglang]. **LMCache** occupies an adjacent niche: rather than a serving engine, it is a standalone KV cache layer that vLLM calls into, offering tiered GPU/CPU/disk/remote storage (Redis, Mooncake, InfiniStore, among others) for cross-instance KV reuse, and, via its NIXL integration, peer-to-peer transfer for disaggregated prefill without recomputing context [@lmcache-2024-turbo; @lmcache-2025-nixl; @lmcache-2026-docs].

### A worked calculation

The bytes that must cross this fabric per request follow directly from model architecture. For a transformer with $L$ layers, $n_{kv}$ KV heads and head dimension $d_h$, storing both $K$ and $V$ at $b$ bytes/element, bytes/token $= 2 \times L \times n_{kv} \times d_h \times b$.

Llama 3 70B uses grouped-query attention with $L=80$ layers, $n_{kv}=8$ KV heads and head dimension $d_h = 8192/64 = 128$ [@meta-2024-llama3]. At FP16 ($b=2$ bytes): $2 \times 80 \times 8 \times 128 \times 2 = 327{,}680$ bytes, i.e. **320 KiB per token**.

For an 8,192-token prompt (Llama 3's native training context), the KV cache to move is $320\text{ KiB} \times 8192 = 2.5\text{ GiB}$ (2.68 GB). At idealized, single-flow line rate:

| Link | 8,192-token prompt (2.5 GiB) | 256-token prompt (80 MiB) |
| --- | ---: | ---: |
| 100 Gb/s | ~215 ms | ~6.7 ms |
| 400 Gb/s | ~54 ms | ~1.7 ms |
| 800 Gb/s | ~27 ms | ~0.8 ms |

These are lower bounds: real RDMA goodput runs below line rate, and Splitwise's own measurements found a roughly constant 5–8 ms floor per transfer from connection and synchronization overhead, independent of payload size [@splitwise]. FP8 KV quantization — one byte per element instead of FP16's two — roughly halves every figure in the table [@vllm-fp8]; KIVI's more aggressive 2-bit asymmetric quantization compresses further still, reporting up to an 8× reduction in KV cache size relative to FP16, not a simple halving [@kivi]. Tensor parallelism changes the picture further: sharding KV heads across $p$ GPUs, each with its own NIC, both divides the per-link payload by roughly $p$ and lets shards move in parallel — the mechanism behind Mooncake's 8×400 Gb/s aggregate figure and SGLang's GPU staging buffer for heterogeneous prefill/decode TP [@qin-2025-mooncake; @sglang-2026-pd].

### When disaggregation does not pay off

The 8,192-token figures make disaggregation an easy trade: 27–215 ms of transfer is small next to the hundreds of milliseconds of queuing delay it removes by isolating a long prefill from an ongoing decode stream [@distserve]. The 256-token case is the opposite regime, and the vendors and projects surveyed above converge on the same warning independently. vLLM states plainly that disaggregated prefill does not raise throughput on its own [@vllm-2026-disaggpf]. Ray Serve's guidance lists short outputs, network limitations and small models as the three cases favoring a colocated deployment, since KV transfer latency "is mostly determined by network bandwidth" and can dominate when transfer is unnecessary [@ray-2026-pd]. NVIDIA's Dynamo documentation is equally direct: disaggregation "is not automatically better. For small models, short prompts, low concurrency, or clusters without a fast KV-transfer fabric, an aggregated deployment is simpler and often faster" [@nvidia-2026-dynamoguide]. The mechanism is the one the worked calculation exposes: at 256 tokens, the theoretical transfer time (under 7 ms even at 100 Gb/s) is already comparable to the fixed RDMA connection/handshake overhead Splitwise measured, and to the cost of recomputing that small a prefix locally — so shipping the request to a remote prefiller pays real network and scheduling cost for compute the decode node's own, already-warm GPU could have done for free, particularly when a high prefix-cache hit rate means little of the prompt is actually uncached. Splitwise made the same point structurally, choosing serialized (not layer-wise-overlapped) transfer for small prompts because, at that size, the saved latency does not justify the added synchronization complexity [@splitwise].

None of this generalizes cleanly to the opposite extreme. Disaggregation's premise rests on prefill being compute-bound and decode memory-bound; at context lengths well beyond the 8K figure above, prefill's own attention cost grows with history length and starts to resemble decode's memory-bandwidth profile, eroding the split the architecture is built on. DeepSeek-V3/R1 is also a reminder that the dense-model arithmetic above does not transfer to large MoE models directly: its prefill and decode pools differ not just in count but in expert-parallelism degree (32 vs. 144) and node count (4 vs. 18), a partitioning problem the per-token KV-byte formula does not capture [@deepseek-2025-inference]. Model size cuts the same way from the other side: for models small enough that both phases fit comfortably in one GPU's compute and memory budget, NVIDIA's own guidance is to keep them aggregated rather than pay disaggregation's fixed operational and network cost for a phase-interference problem that scale has not yet created [@nvidia-2026-dynamoguide].

## The Cache as Storage: Shared and Persistent KV Tiers

Every tier examined so far — GPU HBM, host DRAM, local NVMe — is scoped to one server. Once a KV cache must outlive a single node's process, survive a restart, or be reused by a request that lands on a different GPU, it becomes a storage problem in the literal sense: bytes with a key, a lookup path, a retention policy, and a network in between. Over 2025–2026 this moved from a handful of research systems (Mooncake, AttentionStore) [@qin-2025-mooncake] to a full commercial ecosystem — an open-source caching layer (LMCache), a vendor-neutral tiering API (NVIDIA Dynamo's KV Block Manager), and a new storage-processor product category from NVIDIA itself — plus dated, quantitative benchmark claims from most major storage vendors. This section surveys that ecosystem as of September 2026, then works through when fetching a cached prefix from each tier is actually cheaper than recomputing it.

### Software tiering: LMCache and Dynamo's KV Block Manager

LMCache, the storage layer most widely embedded into vLLM, organizes offload as an ordered fallback: GPU memory → CPU RAM → local disk → remote store [@lmcache-2026-backends]. Its multiprocess mode formalizes this as two tiers: an L1 fast tier (CPU memory, or an NVMe slab reached via GPUDirect Storage/cuFile) holding every chunk currently in use, and a set of L2 "secondary" backends that a `StoreController` pushes to asynchronously and a `PrefetchController` pulls from on a miss [@lmcache-2026-l2storage]. Shipped L2 backends span local disk, Redis/Valkey, Google Cloud Bigtable, Mooncake Store, InfiniStore, NIXL-based stores, and S3-compatible object storage [@lmcache-2026-backends; @lmcache-2026-s3]. Each adapter can declare its own eviction policy (typically LRU against a configured `max_capacity_gb`) and can be marked `shared: true` so several LMCache instances treat one bucket or export as a common, deduplicated pool [@lmcache-2026-l2storage].

NVIDIA Dynamo's KV Block Manager (KVBM) formalizes the same idea as a four-tier hierarchy — G1 (GPU-resident blocks), G2 (pinned host memory), G3 (local SSD, optionally via GDS), and G4 (remote or object storage, which KVBM treats as an opaque blob store) — with independent offload policies (`pass_all`, `presence`, or a least-frequently-used `presence_lfu`) gating each G1→G2→G3 transition [@nvidia-2026-kvbmdesign; @nvidia-2026-kvbmconfig]. KVBM's own configuration reference documents an explicit sizing rule of thumb: the host (G2) cache should be sized above the engine's GPU KV cache and the disk (G3) cache above the host cache, or the system "churns" — offloading blocks it will immediately need back [@nvidia-2026-kvbmconfig]. LMCache's cascading L1/L2 architecture (below) implies the same constraint — an L2 tier undersized relative to L1's working set would force the same evict-and-refetch cycle — but its own documentation does not state a sizing guideline this explicitly.

### Hardware tiering: GDS, NVMe-oF, CXL, and NVIDIA's storage push

GPUDirect Storage (GDS) is the mechanism nearly every vendor below relies on: it lets an NVMe drive or NIC DMA directly into GPU memory, skipping the CPU bounce buffer, and NVIDIA's own guidance reports roughly 25 GB/s achievable per PCIe Gen4 CPU tree (higher on Gen5/BlueField-3-class fabrics), with dynamic routing support for DDN-EXAScaler, VAST-NFS and WekaFS specifically [@nvidia-gds-overview; @nvidia-gds-design]. NVMe over Fabrics (NVMe-oF) extends the same command set across a network fabric; its authors' original design goal was no more than 10 microseconds of added latency over a local drive [@nvmexpress-2016-overview] — a target real deployments approach but do not uniformly hit, since fabric hardware, software stack, and queue depth all matter. CXL memory pooling is the one technology here with no announced KV-cache product as of September 2026: Microsoft's Pond estimates CXL-pooled DRAM adds only 70–90 ns over same-NUMA-node DRAM for an 8–16-socket pool (rising above 180 ns at rack scale) [@li-2023-pond] — cheap enough to be a plausible G2 extension — but none of the vendors surveyed below report using it for KV cache specifically; it remains adjacent rather than deployed.

NVIDIA itself entered the storage-hardware market directly at CES 2026 with BlueField-4 and the Inference Context Memory Storage Platform, claiming up to 5x tokens/second and 5x power efficiency versus "traditional storage" [@nvidia-2026-bluefield4pr]. At GTC 2026 this was detailed as CMX, adding a new "G3.5" Ethernet-attached flash tier — explicitly non-durable, since KV cache is treated as "transient, derived, and recomputable if lost" — bridging GPU/host memory and existing shared storage under the STX reference architecture [@nvidia-2026-cmxblog; @nvidia-2026-stxpr]. General availability across a long partner list is set for the second half of 2026; none of the headline multipliers above are independently reproduced in public benchmarks as of this writing.

### Object storage as a KV tier

Object storage is architecturally the most attractive KV tier — one flat, shared namespace reachable from every node — and the most exposed to overhead that has nothing to do with raw bandwidth. LMCache and Dynamo's KVBM both key objects by chunk (LMCache's default chunk size is 256 tokens; KVBM's G4 blocks are whatever size the engine pages) [@lmcache-2026-s3; @nvidia-2026-kvbmconfig]; for a 70B-class model this puts a single object in the tens of megabytes — large enough to amortize per-request overhead, but coarse enough that a partial-block match still forces a full re-fetch or recompute. Both LMCache's S3 backend and vLLM's own prefix cache identify a block by a hash chained from the previous block's hash and its own token content [@lmcache-2026-s3; @vllm-prefix-design] — the same content-addressing scheme used for cross-request reuse elsewhere in this whitepaper — which means a KV object's key is a deterministic function of tenant-visible content unless a tenant-specific salt is mixed in, precisely the isolation gap vLLM's `cache_salt` option was added to close [@vllm-prefix-design]. Scality's own characterization of plain S3 is blunt: the data path is fast, but "the overhead in S3 is its control path — request signing, authorization, plus metadata lookups" [@scality-2026-labtest], which is why every vendor above pairs the S3 *API* with an RDMA or GPUDirect *data path* rather than shipping bytes over ordinary HTTP. Where that pairing is done, the storage software is often not the bottleneck at all: Scality's own lab test sustained 87% of its test network's measured ceiling while the storage nodes stayed roughly 96% idle [@scality-2026-labtest]. TTL and eviction are handled per-tier rather than globally — LMCache evicts by LRU against a configured capacity watermark [@lmcache-2026-l2storage], KVBM by configurable per-transition policies [@nvidia-2026-kvbmconfig], and Everpure's KVA groups entries into hourly time bins with a distributed clock-sync step so a multi-host fleet agrees on one expiry boundary [@everpure-2026-kva1]. Multi-tenancy is the least settled piece: in a separate VAST Data thought-leadership post, the company's Director of AI Architecture states plainly that once KV cache "leaves the GPU, it contains sensitive user data and is vulnerable to manipulation or reverse engineering by attackers" [@vastdata-2026-memorytier] — a shared, content-addressed, cross-tenant store is exactly the design that needs namespace isolation, not merely the capacity to hold everyone's cache.

### A worked break-even: fetch versus recompute

Take Llama-3-70B (80 layers, $d_{\text{model}} = 8192$, 8 KV heads, head dimension 128, GQA) [@meta-2024-llama3] and a 100,000-token shared prefix. FP16 KV cache per token is $2 \times 80 \times 8 \times 128 \times 2\text{ B} = 327{,}680$ B, so the prefix occupies $\approx 32.8$ GB. Its FP16 weights alone are $\approx 140$ GB, so no single 80 GB H100 can even hold this model. Parallelism regimes vary across the vendor table above, though: Dell's own Llama-3.3-70B benchmark uses tensor parallelism (TP=4 is typical for a 70B-class model on 80 GB GPUs) [@dell-2026-multiturn], VAST's AMD test instead ran the larger-parameter-count GPT-oss-120B at TP=1 on a single MI355X GPU, whose 288 GB of HBM3E holds it without partitioning [@vastdata-2026-amd; @amd-2025-mi355x], and Scality's own benchmark used four models of 4–27B parameters on a single GPU with no NVLink interconnect at all [@scality-2026-labtest] — worth remembering that the "recompute" numbers compared below are not all measured under the same parallelism, or even the same model scale.

Recompute cost is commonly approximated as $2Pn$ FLOPs, a convention — used for MFU accounting since PaLM/Chinchilla-era scaling work — that treats attention's own $O(n^2 d)$ term as a smaller, second-order cost safe to drop [@dao-2022-flashattention]. At $P = 70 \times 10^9$, $n = 10^5$, $2Pn \approx 1.4 \times 10^{16}$ FLOPs. That convention does not hold at this context length: for this architecture, the causally-masked attention term itself is $\approx 2 n^2 d_{\text{model}} L = 2 \times (10^5)^2 \times 8192 \times 80 \approx 1.3 \times 10^{16}$ FLOPs — comparable to, not smaller than, $2Pn$ — because $n = 10^5$ sits close to this model's own crossover point, $n \approx P / (d_{\text{model}} L) \approx 107{,}000$ tokens for causal attention (about half that, non-causal). On one H100 SXM (989.5 TFLOP/s dense BF16 peak) [@nvidia-2023-h100] at an illustrative 20–50% model FLOPs utilization (MFU), the $2Pn$-only estimate gives 28–71 s single-GPU, or roughly 7–18 s at TP=4 — in the same range as Dell's own measured recompute baseline of just over 17 s at a comparable 131K-token context [@dell-2025-kvcache]. Because the attention term is excluded, though, these figures are a lower bound on true recompute cost at this context length rather than a tight estimate — including it would roughly double the high end of the range — and the comparison to Dell's baseline, a different model at a different context length, should be read as order-of-magnitude only.

Figures follow the section's own $10^9$-byte convention throughout (GB, GB/s), not binary GiB; vendor-reported numbers are taken at face value and not independently re-derived for the two-convention difference, which could shift any one row's fetch time by roughly 7%. Every RDMA-class tier fetches faster than even the most aggressive (TP=4, 50% MFU) recompute estimate; the break-even shared-prefix length for these tiers works out to a few dozen tokens at most, since the fixed per-request latency — not raw bandwidth — is what has to be paid down, and it is paid down almost immediately. Plain HTTP object storage is a closer call: at a representative 35% MFU, its per-token transfer cost (~164 μs, at an assumed 2 GB/s parallelized connection) slightly exceeds TP=4's per-token compute cost (~101 μs), so fetch time grows faster than recompute time as the prefix lengthens and there is no length at which it wins; at a lower, still-plausible 20% MFU the ordering flips and plain S3 is faster for this 100,000-token example (though not for very short prefixes, where its latency floor dominates). This knife-edge is specific to the unaccelerated object-storage row — every RDMA-accelerated tier stays faster than recompute across the whole 20–50% MFU range — and it is exactly why Dell, DDN, and Scality all pair the S3 API with an RDMA path underneath rather than shipping large-scale KV fetch over ordinary HTTP.

### Limits

These figures describe cache hits only; a miss still costs a full recompute plus a write-back, and hit rate — not tier speed — usually dominates end-to-end economics [@qin-2025-mooncake]. Smaller or MHA-heavy models carry more KV bytes per parameter, narrowing or reversing the margins above. None of the public benchmarks cited here isolate GPU opportunity cost (a recomputing GPU is a GPU not serving other requests) from wall-clock latency, and none is independently reproduced outside the vendor's own lab. CXL pooling is well characterized in the systems literature but absent from every announced KV-tier product surveyed here. And every multi-tenancy claim above is a vendor assertion about a mechanism — a shared, content-addressed, cross-node cache — whose isolation properties have not been independently audited.

## Evolution in Large-Scale Deployments

KV caching has moved from a single-GPU convenience to a distributed-systems problem in its own right. Early deployments (the GPT-2 era) worked with short context windows and single-digit batch sizes, so a KV cache resident entirely in one GPU's memory was sufficient. Two changes since then have made that assumption obsolete: context windows have grown by roughly three orders of magnitude — from 1,024 tokens in the GPT-2 era [@radford-2019-gpt2] to over 1 million tokens at today's frontier — and serving has moved from single requests on single GPUs to thousands of concurrent sessions spread across multi-GPU, multi-node clusters. This section traces both threads through September 2026 and describes how KV cache management has had to keep pace — sharding across GPUs, pooling and swapping between memory tiers, and, increasingly, surviving hardware failure. The detailed mechanics of prefill/decode disaggregation, prefix-cache reuse, and multi-tier storage are treated in dedicated sections elsewhere in this whitepaper; here the focus is the trajectory, not the internals.

### Context windows: from 32K to the million-token era

By 2023, GPT-4 shipped a 32K-token context option and Claude reached 100K [@gpt4; @claude100k] — already an order of magnitude beyond the GPT-2 era. Three years on, the frontier has moved again, though unevenly across vendors and model tiers:

| Anthropic Claude | Claude: 100K tokens [@claude100k] | Claude Opus 5 and Sonnet 5 (and, earlier, Sonnet 4.6 and Opus 4.6–4.8): 1M tokens; Claude Sonnet 4.5 remains at 200K [@anthropic-2026-contextwindows] |

Two qualifications matter here. First, growth was not monotonic even within one vendor's own lineup: OpenAI's initial GPT-5 release in August 2025 held at 400K tokens, and only the later GPT-5.4 release reached the 1M-token class [@openai-2025-gpt5launch; @openai-2026-gpt54] — and vendors continue to ship smaller, cheaper model tiers at the older 200K-token size alongside their flagship [@anthropic-2026-contextwindows]. Second, "context window" as marketed is an input/output token budget, not a guarantee of usable accuracy at that length: Anthropic's own documentation states that retrieval and reasoning accuracy degrade as token count grows, a phenomenon it calls context rot, well before the nominal window fills [@anthropic-2026-contextwindows]. Research systems, meanwhile, have pushed further still: HeadInfer's head-wise CPU offloading — keeping only a subset of attention heads' KV cache on GPU at any time and computing the rest from CPU-resident data — reports its headline capacity result as 4-million-token decoding for an 8B model on a single 24 GB consumer GPU; a separate, more conservative roofline analysis in the same paper targets a 1-million-token sequence and reports cutting that sequence's on-GPU KV cache from 128 GB to 1 GB (total GPU memory from 207 GB to 17 GB) for the same model [@headinfer]. This section cites the larger, single-GPU capacity figure; either way, it is a research offload technique evaluated on a narrow model/hardware pairing, not a production-serving figure, and a useful reminder that "context length achievable in a paper" and "context length served at scale, for every concurrent user" are different claims. Every one of these increases multiplies KV cache size directly, since cache size per request scales linearly with sequence length; a service offering a 1M-token window must provision KV cache capacity an order of magnitude larger than one offering 100K, for every concurrent long-context session.

### Sharding the KV cache across GPUs

When a model does not fit on one GPU, tensor parallelism partitions each transformer layer's weight matrices across GPUs, and the KV cache is partitioned along with them. In the scheme introduced by Megatron-LM, the query, key and value projections are split column-wise so that the matrix multiply for each attention head executes entirely on one GPU; each GPU therefore holds and updates the K/V state only for the attention heads assigned to it, with no cross-GPU communication needed until the output projection's single all-reduce [@shoeybi-2019-megatron]. This is genuine per-GPU sharding of the cache, not replication — under this scheme, and unlike duplicated weights such as layer-norm parameters, each GPU's slice of the KV cache is unique.

That sharding has a hard limit the original scheme does not surface. Grouped-query, multi-query and multi-head-latent attention variants (see "Shrinking the Cache at the Source") use far fewer KV heads than query heads — sometimes a single shared KV head, as in multi-head latent attention. Once tensor-parallel width exceeds the number of KV heads, there is nothing left to shard: current serving engines instead replicate the full KV cache onto every GPU beyond that point, which wastes HBM and caps the batch size a cluster can serve at long context lengths [@bhatia-2025-helix]. NVIDIA's Helix Parallelism, published in mid-2025, targets exactly this ceiling by decoupling the parallelism strategy used for attention from the one used for the feed-forward network within the same layer: during attention, tensor-parallel width is kept at or below the KV-head count and any remaining GPUs instead shard the KV cache along the sequence dimension (KV parallelism); the same GPU pool is then re-provisioned at full tensor/expert-parallel width for the feed-forward computation [@bhatia-2025-helix]. On simulated million-token-plus decoding of DeepSeek-R1 (which uses a single effective KV head) on NVIDIA's GB200 NVL72 hardware at FP4 precision, the authors — NVIDIA researchers — report up to 32× more concurrent users at a fixed latency budget (and up to 1.5× lower token-to-token latency at low concurrency) compared to prior sharding strategies; for a dense 405B-parameter model with 8 KV heads (Llama-405B-class GQA), the reported gain is a narrower 4× throughput and batch-capacity improvement at 1.13× better peak interactivity [@bhatia-2025-helix]. These are vendor-affiliated, hardware- and precision-specific simulation results on models that do not yet natively ship million-token contexts, not a general production-deployment claim, but they mark where sharding strategy is heading as KV-head-sparse architectures meet ever-longer contexts. The same underlying idea — shard the KV cache along the sequence axis, not only the head axis — appears more generally as context parallelism. Training stacks such as Megatron-LM support it as a first-class parallelism dimension alongside tensor and pipeline parallelism, exchanging KV shards between GPUs via all-gather (forward pass) and reduce-scatter (backward pass) in a ring topology [@nvidia-megatron-cp-docs]; the same sequence-sharding idea has since been carried over to the decode phase of inference serving specifically — NVIDIA's TensorRT-LLM ships Helix as, in its own words, "a context parallelism (CP) technique for the decode/generation phase of LLM inference" [@nvidia-2026-trtllmhelix].

### Disaggregation, pooling and swapping

Beyond sharding a single model's cache, large deployments increasingly split *stages* of a request onto different hardware pools — prefill on compute-optimized GPUs, decode on memory-bandwidth-optimized GPUs [@splitwise; @distserve; @doubao15] — and combine that split with cache-aware request routing and cross-tier offload as one coordinated system rather than separate point techniques, as in NVIDIA's Dynamo serving stack [@elmeleegy-2025-dynamo]. That disaggregation, and the prefix-cache-aware routing layered on top of it, are covered in their own section of this whitepaper; the relevant point here is that KV cache placement, not model placement, has become the primary scheduling variable in these systems.

Within a single deployment, memory pooling addresses a related inefficiency: pre-allocating each session's maximum possible KV cache wastes capacity, since most sessions never reach it. vLLM's page-level pool reclaims this by allocating cache blocks on demand rather than per session [@vllm-blog]. The *DéjàVu* system (ICML 2024) goes further for **pipeline-parallel** deployments specifically: pipeline parallelism creates idle "bubbles" because prompt processing and token generation have very different per-step latency, and DéjàVu's *microbatch swapping* moves a microbatch's KV cache to CPU memory while that microbatch is not actively being computed on, freeing GPU memory for other microbatches in flight [@dejavu]. The authors report this swapping alone improves throughput by up to 1.8× by allowing larger batch sizes, and up to 2× overall against FasterTransformer when combined with their prompt/token disaggregation [@dejavu] — figures specific to the pipeline-parallel serving setups and cloud deployments the paper evaluates, not a general claim about swapping under every parallelism scheme.

### Fault tolerance

DéjàVu also replicates KV cache state to persistent storage or remote CPU memory as it streams, so that a GPU failure does not require regenerating a request from scratch: on failure, the system restores the most recently replicated state to a healthy GPU and resumes generation from the last completed token rather than the beginning of the sequence [@dejavu]. Under injected failures, the authors report a 1.54× reduction in microbatch latency relative to a non-fault-tolerant baseline [@dejavu]. This is narrower than "KV caches are now routinely persisted for fault tolerance in production" — it is one research system's mechanism, evaluated in pipeline-parallel deployments, and its cost (continuously streaming replica writes) is only worth paying when failure rates and request lengths make losing in-flight generation expensive enough to justify it.

### A widening memory hierarchy

The other axis of change is which physical memory a KV cache is allowed to live in at all. Micron's own September 2026 analysis of KV cache growth frames current serving infrastructure around a five-tier hierarchy running from GPU HBM (10–100 GB per GPU at 1–20 TB/s, millisecond-to-second residency for active token generation), through DDR5 main memory (100–500 GB/s, seconds to minutes) and disaggregated expansion memory (100–200 GB/s, minutes to hours), down to NVMe SSDs (10s–100s of TB per GPU at 20–200 GB/s, hours-to-days residency for multi-turn agentic workflows) and networked object storage for cache that must persist across the turns of a long agentic session — organized explicitly by how long a piece of KV cache needs to stay reachable rather than by capacity alone. Set against that same tier table, the vendor's claim of validating NVMe-based KV cache offload "with zero throughput penalty" across hundreds of test configurations for agentic workloads is plausible chiefly because that offload targets the hours-to-days residency tier: a reload that happens once per multi-turn boundary and is overlapped with inter-turn "think" or tool-call time looks very different from one that happens on every decode step, where the 50–1000× bandwidth gap between HBM and NVMe shown in the same table would otherwise dominate. Absent a disclosed hardware configuration or baseline, this remains an unverified vendor claim (vendor-reported) [@vazhkudai-2026-kvcache]. On the HBM tier specifically, Micron's HBM4 — in volume production for NVIDIA's Vera Rubin platform since the first quarter of 2026 — delivers over 2.8 TB/s of bandwidth per stack, more than double the prior HBM3E generation, marketed explicitly against "context windows spanning millions of tokens" (vendor-reported) [@micron-2026-hbm4; @micron-2026-verarubin]. Whether that generational bandwidth growth keeps pace with KV cache demand growth is a separate, open question this section does not attempt to settle; the narrower point is that memory vendors are now designing and marketing hardware generations explicitly around KV cache residency and reuse, which was not true in the sub-100K-token era this section opened with.

## Workload Trends Driving KV Demand (2024–2026)

The preceding sections treat KV cache size largely as a function of sequence length, batch size, and model width. Between 2024 and 2026, several shifts in how models are built and used have pushed on all three variables at once: context windows measured in millions rather than thousands of tokens; reasoning models that spend tens of thousands of tokens deciding what to say before saying it; agentic and coding workloads that re-send large, mostly static contexts on every step rather than issuing one-shot prompts; and new decoding and routing schemes — speculative decoding variants and mixture-of-experts (MoE) — that change *how* KV cache is produced and shared without necessarily shrinking it. This section quantifies each trend and, where the evidence is mixed, says so.

### Long context windows: from kilotokens to megatokens

By September 2026, a 1-million-token context window is a mainstream, not exotic, spec among frontier and open models. Google reports several Gemini models with windows of "1 million or more" tokens [@google-2026-longcontext]. Meta's Llama 4 Maverick (17B active / 400B total, MoE) ships a 1M-token window and Llama 4 Scout (17B active / 109B total) an "industry-leading" 10M [@meta-2025-llama4]. Advertised context length is not effective context, however: Meta published no long-context evaluation of Scout beyond needle-in-a-haystack retrieval, and independent commentary at launch noted that harder long-context evaluations (RULER, NoLiMa) were absent and that early third-party results "range from medium to bad and confusing" [@lambert-2025-llama4]; as of September 2026, Scout scores 27.3% on the independent Fiction.LiveBench long-context comprehension benchmark at 120K tokens, ranking 32nd of 35 tested model configurations — well behind several models with far smaller advertised windows [@benchleader-2026-fictionlivebench]. OpenAI's GPT-4.1 extended context to "up to 1 million tokens" [@openai-2025-gpt41]. Alibaba's Qwen2.5-1M extends the open-weight 7B and 14B Qwen2.5 models to 1M tokens via long-context pretraining and length extrapolation, and states the deployment cost directly: serving the 1M window needs at least 120 GB of VRAM (total, across GPUs) for the 7B model and 320 GB for the 14B model [@qwen-2025-1m]. Anthropic documents several current Claude tiers with a 1M-token window at standard pricing, with everything in a request — system prompt, tool definitions, tool results, and extended-thinking output — counted against it [@anthropic-2026-contextwindows].

| Claude (Anthropic, several current tiers) | up to 1,000,000 tokens | [@anthropic-2026-contextwindows] |

The KV cost is easy to size. Using Mixtral's published GQA configuration purely as an illustrative example — 32 layers, 8 KV heads, head dimension 128 [@mistral-2024-mixtral] — the cache holds $2 \times 8 \times 128 \times 32 = 65{,}536$ elements per token, about 128 KiB at bf16, or roughly 122 GiB for one sequence's K/V tensors alone at 1,000,000 tokens and batch size 1, before weights or activations. Qwen2.5-7B-Instruct-1M's real, published attention configuration is considerably smaller — 28 layers, 4 KV heads, head dimension 128 [@qwen-2025-1m] — giving $2 \times 4 \times 128 \times 28 = 28{,}672$ elements per token (56 KiB at bf16) and roughly 53 GiB of KV cache alone at 1,000,000 tokens: about 48% of the 120 GB total, multi-GPU VRAM budget Qwen's own deployment guidance specifies for serving that model's 1M window across up to four GPUs in tensor parallel [@qwen-2025-1m]. That 120 GB figure covers model weights, chunked-prefill activation buffers, and the MInference sparse-attention structures needed to make 1M-token prefill tractable, not KV cache alone [@qwen-2025-1m] — a reminder that 1M-context serving depends on the offload, quantization, and paging techniques covered elsewhere in this paper, not on raw HBM capacity.

### Reasoning models: decode-heavy generation grows the cache long after prefill ends

Reasoning models generate a chain-of-thought before (or instead of) a direct answer, and that chain occupies the KV cache like any other generated token, visible or not. During RL training, DeepSeek-R1(-Zero) rollouts were capped at 32,768 tokens, raised to 65,536 tokens after step 8.2k [@deepseek-2025-r1], and its authors report that average response length grew on its own during training as the model "naturally learns to solve reasoning tasks with more thinking time" [@deepseek-2025-r1]. OpenAI documents the same mechanic for deployed models: reasoning tokens are hidden from the API response but "still occupy space in the model's context window and are billed as output tokens," ranging "from a few hundred to tens of thousands" per query, with a recommended 25,000-token reservation [@openai-2026-reasoning]. MLCommons' MLPerf Inference v5.1 benchmark sets a maximum output sequence length of 20,000 tokens for DeepSeek-R1 — "the highest yet in the MLPerf Inference benchmark suite" — and reports mean input/output lengths of 800 and 3,880 tokens on its curated reasoning dataset [@mlcommons-2025-dsr1]. For a similarly short visible answer, then, a reasoning model's decode-phase KV cache can be many times larger than a non-reasoning model's, since the trace must stay resident to condition every later token.

This growth is not unconditionally beneficial. LongReasonArena, scaling required reasoning length toward 1M tokens, finds accuracy declining log-linearly with the number of reasoning steps required, with DeepSeek-R1 reaching only 7.5% accuracy at its hardest tier [@ding-2025-longreasonarena]. Longer chains-of-thought can buy diminishing — even negligible — returns while still paying their full KV cost, so provisioning should follow measured output-length distributions, not worst-case token budgets alone.

### Agentic and coding workloads: long, repeatedly re-sent context and tool output

Agentic and coding workloads differ from a single long prompt: a large, mostly static context (system prompt, tool schemas, accumulated history) plus fresh tool output is re-sent on *every* step of a multi-step loop. Anthropic's account of building Claude Code states that "we build our entire harness around prompt caching," running alerts — and declaring incidents — on cache hit rate, and orders every request static-first (system prompt and tools, then project memory, then session context, then conversation) to keep the shared, cacheable prefix as large as possible; changing the tool set mid-conversation "invalidates the cache for the entire conversation" [@anthropic-2026-claudecode]. Anthropic's original prompt-caching release quantifies the payoff: a cached 100,000-token prompt cuts time-to-first-token from 11.5 s to 2.4 s (−79%) and cost by up to 90%; a ten-turn conversation with a long system prompt cuts TTFT from ~10 s to ~2.5 s (−75%) [@anthropic-2024-promptcaching].

Accumulated context has grown past what agent frameworks were sized for. SWE-agent originally budgeted 128K–200K-token windows as "sufficient ... to interact for several turns" [@yang-2024-sweagent]. A 2026 study's own corpus of long-horizon coding-agent trajectories shows an average of 87.4 steps per trajectory and 13,044 tokens of context added per step (median 10,875; max 65,536) [@liu-2026-cat], and the same authors diagnose "context explosion" as the default failure mode of the unmanaged, append-only context handling their method is built to replace. A dataset of 80,036 SWE-agent trajectories shows the same asymmetry seen with reasoning length: resolved runs average 8,352 tokens of accumulated context, unresolved ones — which keep running rather than submitting — average 15,241 [@nebius-2025-swetraj]; SWE-agent's own analysis finds 93.0% of resolved instances submit before exhausting their budget, versus 69.0% overall [@yang-2024-sweagent] — agents succeed quickly and fail slowly, and the slow failures drive peak KV demand. This is partly a design artifact rather than an intrinsic cost: a compression-aware agent in the same 2026 study holds context "stable at approximately 35k tokens" across hundreds of rounds where an append-only baseline exhausts its window [@liu-2026-cat].

### Multi-turn chat: a smaller per-session footprint, multiplied by concurrency

Ordinary consumer chat traffic is comparatively modest: across one million real conversations, LMSYS-Chat-1M reports an average of 2.0 turns per session, 69.5 tokens per prompt, and 214.5 tokens per response [@zheng-2023-lmsys] — a per-session KV footprint of tens of kilobytes, not gigabytes. Aggregate KV pressure on a serving fleet instead scales with concurrency times per-session footprint, and it is the long tail — reasoning, agentic, and long-document sessions — that sets peak memory demand, not the median chat turn; a fleet provisioned only for LMSYS-Chat-1M-like medians would be caught out by a mix that includes even a modest share of the 100K+-token sessions described above.

### Speculative decoding variants: verification breadth trades one KV cache for another

Classic speculative decoding [@leviathan; @chen-spec] runs a separate, smaller draft model that maintains its own KV cache alongside the target's, effectively doubling the number of caches per in-flight request. Newer variants draft from the target model itself instead. Medusa adds $K$ extra decoding heads onto the target backbone and verifies several candidates at once with tree-structured attention, reaching 2.2× (frozen backbone) to 2.3–2.8× (jointly fine-tuned) speedup with no separate draft model or cache [@cai-2024-medusa]. EAGLE-3 predicts tokens directly from fused low-, mid-, and high-layer features of the target model, reporting speedups up to 6.5× (1.4× over EAGLE-2) and a 38–40% throughput gain at batch size 64 in SGLang [@li-2025-eagle3]. DeepSeek-V3 trains one extra sequential module for multi-token prediction (MTP); at inference it can be discarded or repurposed as a self-speculative draft, with an 85–90% acceptance rate for the second predicted token and a 1.8× tokens-per-second improvement [@deepseek-2024-v3].

The common thread: Medusa, EAGLE-3, and MTP replace a second full model's KV cache with a small auxiliary cache or nothing beyond the target's own, in exchange for wider — but transient — per-step attention while candidates are verified before rejected branches are pruned. The gains are not unconditional: EAGLE-3's authors note that "speculative sampling is often thought to reduce throughput at large batch sizes" [@li-2025-eagle3], since decode is already closer to compute-bound at high occupancy, leaving less slack to exploit — the batch-64 result is not a batch-independent guarantee.

### Mixture-of-experts: sparse compute, but attention — and its cache — stays dense

An MoE layer sparsifies only the feed-forward sub-block; attention, and therefore the KV cache, still runs over every token regardless of which experts are routed to. KV cache size is set by attention configuration — layers, heads, head dimension — not by active-parameter count, and the two can be decoupled in either direction. Mixtral 8x7B illustrates one direction: 47B total parameters, 13B active per token, yet an attention stack (32 layers, 8 KV heads, head dimension 128) identical to the 7B-parameter dense Mistral model it is built from [@mistral-2024-mixtral] — its KV cache per token is that of a 7B-class dense model despite 13B-class active compute.

The trend this section's title points to runs the other way: scaling attention depth/width to a large *total*-parameter budget while keeping active compute low via sparse routing. DeepSeek-V3 (671B total, 37B active) uses 61 attention layers and 128 heads — depth and width typical of a far larger dense model. Applying DeepSeek-V2's published standard-attention formula, $2 n_h d_h l$ [@deepseek-2024-mla], to DeepSeek-V3's released configuration (128 heads, 192-dimension key and 128-dimension value per head, 61 layers) gives roughly $128 \times 320 \times 61 \approx 2.5$ million elements per token for an equivalent standard cache, versus DeepSeek-V3's actual Multi-head Latent Attention (MLA) cache of $(d_c + d_h^{R}) \times l = (512+64) \times 61 = 35{,}136$ elements — about 71× smaller [@deepseek-2024-v3]. DeepSeek-V2 reports the same mechanism cutting KV cache 93.3% and lifting maximum throughput 5.76× versus the dense DeepSeek 67B it replaced — DeepSeek's own figures, measured on a single node of 8 H800 GPUs under the prompt/generation-length distribution of DeepSeek's actually-deployed 67B service, with both models' KV caches additionally quantized to 6 bits per element for that deployment [@deepseek-2024-mla].

| Model | Total / active params | Attention config | KV cache per token (elements) |
| --- | --- | --- | --- |
| Mixtral 8x7B [@mistral-2024-mixtral] | 47B / 13B | 32 layers, 8 KV heads (GQA), $d_h$=128 | 65,536 |
| DeepSeek-V3, hypothetical standard MHA [@deepseek-2024-mla] | 671B / 37B | 61 layers, 128 heads, 320-dim K+V per head | ≈2,498,560 |
| DeepSeek-V3, actual MLA [@deepseek-2024-v3; @deepseek-2024-mla] | 671B / 37B | 61 layers, latent rank 512 + rotary 64 | 35,136 |

This is architecture-dependent, not a universal law of MoE: Mixtral keeps KV cache small by reusing a small dense model's attention stack, while DeepSeek shows the opposite is possible when depth and width instead track the *total*-parameter budget. The latter pattern is why KV-compressing designs like MLA, not offload or paging alone, have become part of frontier MoE architecture — though MLA is not free: efficient serving requires purpose-built low-rank attention kernels rather than standard attention-kernel libraries, as DeepSeek's own FlashMLA kernels illustrate [@deepseek-2025-flashmla], an engineering cost additional to the memory-hierarchy techniques discussed elsewhere in this paper.

## Measuring and Pricing the Cache

The preceding sections argue that KV caching turns prefill compute into a one-time cost and decode into a memory-bandwidth problem. Whether that trade is worth making in a given deployment is empirical, not architectural: it depends on how much latency and throughput the cache buys under a realistic workload, and what that saved compute is worth in dollars. This section covers both — the metrics and tools used to measure cache effects, and the public pricing and hardware-cost data needed to turn a measured effect into a dollar figure.

### Metrics that separate cache effects from everything else

Four request-level metrics dominate LLM serving evaluation [@databricks; @nim-metrics]. **Time to first token (TTFT)** is the latency from request submission to the first streamed token, and it bundles queueing, network, and prefill compute — the last of which shrinks whenever a prefix is served from cache instead of recomputed. **Inter-token latency (ITL)**, also called time per output token (TPOT), is the average gap between successive output tokens during decode; vLLM computes it per request as $\text{TPOT} = (\text{e2e latency} - \text{TTFT}) / (\text{output tokens} - 1)$ [@vllm-2025-benchcli]. **End-to-end latency** is $\text{TTFT} + \text{generation time}$ [@nim-metrics]. **Throughput** (tokens/s, aggregate or per-GPU) says how much work a system completes but says nothing about whether any individual request met a latency bound.

That gap motivates **goodput**: the request rate a system sustains while satisfying a joint latency SLO (e.g., TTFT ≤ 2 s *and* TPOT ≤ 50 ms), as opposed to raw throughput, which counts an over-deadline request the same as an on-time one [@distserve]. vLLM's benchmark client operationalizes this directly — `--goodput ttft:2000 tpot:50` reports the fraction of requests meeting both bounds, distinct from `request_throughput` [@vllm-2025-benchcli]. NVIDIA's AIPerf adds SLA-attainment analysis and Pareto-frontier plots of throughput-per-GPU against tokens-per-second-per-user, so the throughput/latency trade-off, not either number alone, is the reported result [@nvidia-2026-aiperf]. A cache that raises throughput while quietly missing more SLOs — say, by admitting more concurrent requests than the freed memory can serve at the target TPOT — is not a net win; goodput and SLO attainment are what should be reported, not tokens/s alone.

### Benchmark suites

**MLPerf Inference** is the closest thing to a standardized cross-vendor comparison. Its Server scenario enforces published p99 TTFT/TPOT bounds per model, while Offline measures unconstrained bulk throughput with no latency requirement — the two are not interchangeable, and citing an Offline tokens/s figure as evidence of interactive-serving capability is a category error [@mlcommons-2026-inferencerules]. The bounds have tightened as usage has shifted toward lower-latency, agentic workloads: Llama 2 70B's Conversational category kept its original 2,000 ms/200 ms TTFT/TPOT limits but gained a new Interactive category at 450 ms/40 ms (25 tok/s), while the newly added Llama 3.1 405B benchmark runs at 6,000 ms/175 ms (Server) and 4,500 ms/80 ms (Interactive) [@mlcommons-2025-llmv5; @mlcommons-2026-inferencerules].

**SemiAnalysis InferenceMAX** (now InferenceX) is an open-source, continuously refreshed benchmark across vLLM, SGLang, and TensorRT-LLM on current accelerators; its central metric is cost per million tokens as a function of interactivity (tokens/s/user), normalized by each system's total-cost-of-ownership per GPU-hour rather than list price, since a chip with lower throughput but lower TCO can still win on $/Mtok [@semianalysis-2025-inferencemax]. **vLLM's `vllm bench serve`** and **SGLang's `bench_serving`** are the de facto client-side tools for both projects, reporting TTFT/TPOT/ITL/e2e-latency percentiles and, for vLLM, goodput against configurable SLOs; both document that a server's default-on prefix cache can silently contaminate repeated runs (see below) [@vllm-2025-benchcli; @sglang-2025-bench]. **LMCache** and **NVIDIA Dynamo** ship KV-cache-specific benchmarks: LMCache's multi-turn benchmark isolates prefill acceleration under realistic shared-prefix conversation traces [@gpustack-2026-lmcacheeval], while Dynamo's disaggregated-serving flow validates predicted TTFT/TPOT against measured values and its deployment walkthrough warns that KV transfer without RDMA degrades TTFT by roughly 40× (355 ms to 10+ seconds) in that illustrative configuration [@nvidia-2026-dynamo-v102]; a separate, more detailed NVIDIA communication guide breaks the same failure mode down by transport and reports a wider, configuration-dependent range on different reference hardware — from +37 ms overhead with AWS EFA plus GPUDirect to +90–100 s under a TCP fallback (roughly 200–500×) — underscoring how strongly the multiplier depends on the specific interconnect rather than being a fixed constant [@nvidia-2026-dynamocomm]. **NVIDIA GenAI-Perf/AIPerf** is the general-purpose client for OpenAI-compatible endpoints, with concurrency sweeps, cache-hit-ratio sweeps, and goodput/SLA analysis built in [@nvidia-2026-aiperf].

### Pitfalls

Benchmark documentation increasingly warns about one specific, quantified failure mode: a deterministic synthetic-prompt generator (fixed seed) rerun against a long-lived server with prefix caching on by default silently replays cache-hit prompts. A reproduced case on vLLM's benchmark client — a DGX Spark GB10 running Qwen3-30B-A3B under vLLM 0.19.2rc1 — showed 49× lower mean TTFT, 34% lower TPOT, and 2.32× higher throughput at a 16K-token input length between a cold run and a cache-contaminated run of the identical configuration; re-measured cold across an ascending-concurrency sweep, the contamination was non-uniform rather than a fixed offset, inflating apparent TPOT by +59.3% at concurrency 4 and +76.0% at concurrency 8 before falling to +25.0% at concurrency 16, once that cell's ~1M input tokens had exceeded the KV cache and evicted most of the earlier shared prefixes [@vllm-2026-benchpitfall]. A controlled H100 study found prefix reuse worth a real 5–6.5× TTFT reduction at an 8,192-token shared prefix, but also found that which serving runtime "wins" on tail latency flips by 2.4–9.2× depending purely on arrival pattern (burst vs. fixed-rate) at fixed concurrency — a single synthetic workload does not generalize across arrival patterns, model sizes, or hardware [@shewale-2026-prefixbench]. More generally, closed-loop (fixed-concurrency) tests report throughput at one operating point and hide where latency blows up, whereas open-loop (fixed-arrival-rate) tests reveal the saturation curve; a discarded warm-up period and enough samples for the reported percentile (roughly 1,000+ for p99) are both necessary for the numbers to mean anything [@kunwar-2026-benchmarking]. Finally, a benchmark run entirely at one cache state — always warm or always cold — will not resemble production, where hit rate is a distribution: a blend of 70% warm (400 ms) / 30% cold (1.8 s) requests gives an unremarkable mean but a p95 dominated by the cold tail, exactly the SLO-relevant number — illustrated there for hosted-API prompt caching, but the same hit-rate-as-a-distribution argument applies equally to self-hosted prefix-cache benchmarking [@tianpan-2026-coldcache].

### Pricing the cache: cost per million tokens vs. hit rate

Public API pricing gives a lower bound on what a cache hit is worth, since it is what a customer would otherwise pay to recompute the same tokens. For a base (uncached) input price $P$ and a cached-input price $rP$ (so $r$ is the fraction of the base price a cache hit costs), the blended price per million input tokens at hit rate $h$ is:

$$P(h) = P\left[(1-h) + hr\right] = P\left[1 - h(1-r)\right]$$

As of September 2026, three major providers price cache reads at $r \approx 0.1$ (a 90% discount) on comparable mid-tier models: OpenAI's GPT-6 Sol ($2.00 base / $0.20 cached, short-context tier) [@openai-2026-pricing], Anthropic's Claude Sonnet 5 ($2.00 base / $0.20 cache-read) [@anthropic-2026-promptcaching], and Google's Gemini 3.8 Flash ($0.75 base / $0.075 cached, standard paid tier, pricing through December 31, 2026) [@google-2026-geminipricing; @google-2026-geminioptimization].

| Hit rate $h$ | OpenAI GPT-6 Sol | Anthropic Claude Sonnet 5 | Google Gemini 3.8 Flash |
|---:|---:|---:|---:|
| 0% | $2.00 | $2.00 | $0.75 |
| 50% | $1.10 | $1.10 | $0.4125 |
| 90% | $0.38 | $0.38 | $0.1425 |

*Blended cost per 1M input tokens, $P(h)=P[1-h(1-r)]$, $r=0.1$ for all three [@openai-2026-pricing; @anthropic-2026-promptcaching; @google-2026-geminipricing]. Google's per-token-storage caching surcharge is omitted from this table, as are all three vendors' cache-write charges (discussed below).*

At $r=0.1$, savings simplify to $0.9h$: an 81% cost reduction at a 90% hit rate. This is not a fixed physical constant, though — it is a per-model, per-vendor, and per-generation business decision. OpenAI's own historical pricing shows $r$ ranging from 0.5 (GPT-4o, October 2024) to 0.25 (GPT-4.1) to 0.1 (GPT-5-nano, GPT-5.2) as inference-serving efficiency improved [@openai-2025-cachingcookbook]; at $r=0.5$, the same 90% hit rate yields only a 45% saving, half the headline figure above. The formula also omits the cache-write charge (1.25–2× the base price, depending on cache lifetime), which both OpenAI and Anthropic now bill on a first write; a prefix must be read back at least once (5-minute cache) or roughly twice (1-hour cache) before writing it pays for itself at all [@openai-2026-promptcaching; @anthropic-2026-promptcaching]. Put differently, hit rate alone is an incomplete predictor of savings — a high hit rate on prefixes that are each read only once after being written can cost *more* than no caching, which is precisely the KV-cache-as-prefill-avoidance mechanism this whitepaper describes, made visible in a bill [@anthropic-2026-costreduction].

### GPU-hour cost of avoided prefill compute

Self-hosted deployments can price a cache hit directly in avoided GPU-hours rather than through a vendor's per-token rate. LMCache's published multi-turn benchmark (Qwen3-8B, single NVIDIA RTX 4090 24GB, vLLM 0.10.1.1, 20K-token shared-prefix conversations) measured mean TTFT drop from 5.07 s without cache reuse to 2.09 s with it — 2.98 s of prefill recomputation avoided per request [@gpustack-2026-lmcacheeval]. Scaled to 1 million such requests, that is roughly 828 GPU-hours of avoided prefill-blocked time, priced at two current on-demand cloud rates for datacenter H100s:

| | Value |
|---|---:|
| TTFT saved per request | 2.98 s |
| Avoided GPU-time @ 1M requests | ≈828 GPU-hours |
| @ CoreWeave on-demand H100 ($6.16/GPU-hr, 8×80GB node) | ≈$5,100 |
| @ Lambda Labs on-demand H100 ($2.99/GPU-hr, 8×80GB node) | ≈$2,475 |

*[@gpustack-2026-lmcacheeval; @coreweave-2026-pricing; @lambda-2026-pricing]. On-demand GPU pricing is a snapshot and varies by region, spot vs. reserved terms, and provider.*

Two limits apply. First, the benchmark ran on an 8B model on a single consumer GPU; prefill cost per token, and therefore the absolute seconds saved, scales with model size and differs on datacenter accelerators, so this is an order-of-magnitude illustration, not a validated prediction for a 70B- or 405B-class deployment. That consumer GPU also has roughly a third of an H100 SXM's HBM bandwidth (1,008 GB/s vs. ~3 TB/s aggregate [@nvidia-2022-ada; @micron]) and no comparable FP8 tensor-core throughput, so a second of freed RTX 4090 prefill time is not the same quantity of compute as a second of freed H100 time; pricing the former at the latter's hourly rate is a further approximation layered on top of the model-size mismatch, not a restatement of it. Second, "avoided GPU-hours" is an upper bound on freed serving *capacity*, not a guaranteed dollar saving — it is realized only if that capacity is actually resold or reused for other requests; on an under-utilized server it simply shows up as idle time. As with token pricing, the dollar figure moves by more than 2× just from which cloud market it is priced against, underscoring that any single-number cache ROI claim needs its hardware and pricing baseline stated alongside it.

## Security, Privacy and Integrity of Shared KV Caches

Every optimization discussed so far in this whitepaper – prefix sharing, disaggregated prefill/decode, offload to CPU or NVMe, and persistent multi-tier stores such as Mooncake – makes the KV cache *shared* and *long-lived* rather than private and ephemeral to a single request. That shift has a security cost: a KV cache's presence, timing behavior, and in some cases raw contents are all correlated with the prompt that produced it. Once a cache is shared across tenants or persisted outside GPU memory, three risks follow – timing side channels that leak prompt content through cache-hit signals, tampering once caches live in shared or remote storage, and the fact that KV tensors are a derived, sometimes invertible, representation of the prompt that must itself be protected at rest and in transit.

### Timing side channels: cache hits leak prompt content

Prefix caching (Section 2) accelerates a request whose prompt shares a prefix with something already cached, and the speedup is visible externally as a lower Time to First Token. If the cache is shared across users, that timing difference becomes an oracle: an attacker who can measure TTFT can test whether a guessed prefix matches another tenant's cached prompt. Song et al. formalized this as a family of timing side channels in production LLM serving systems, targeting both the KV cache and semantic response caches (e.g. GPTCache) [@song-2025-earlybird]. Using a threshold-based classifier on timing measurements plus an incremental, token-by-token search that exploits the prefix-match requirement, they recovered system and peer-user prompts with an average accuracy of 89.0% at a cost of about 112.72 queries per recovered token in black-box tests against real serving stacks; a related "peeping neighbor" attack against semantic caches reached 81.4% accuracy in a single trial, improving to 95.4% after 5 trials under GPTCache's default settings [@song-2025-earlybird]. As a worked illustration: recovering a 50-token system prompt at that measured rate costs on the order of $50 \times 112.7 \approx 5{,}600$ queries – expensive against a rate-limited API, cheap against an unthrottled internal service. Independently, Zheng et al.'s InputSnatch pairs a learned input constructor with statistical time-fitting to attack both prefix caching (vLLM) and semantic caching (GPTCache), without privileged access beyond a standard client [@zheng-2024-inputsnatch]. Wu et al. showed the channel need not be raw latency at all: their PROMPTPEEK attack exploits the *change in serving order* under longest-prefix-match scheduling, inferring cache hits from where a response lands relative to decoy requests, reconstructing prompts with 99%, 98%, and 95% success under decreasing levels of attacker background knowledge on Llama-2-13B/A100 [@wu-2025-promptpeek]. These are not lab-only curiosities: an independent statistical audit of 17 production LLM APIs (Sept.–Oct. 2024) found prompt caching enabled in 8 and cross-user ("global") sharing in 7, including a since-patched OpenAI embedding endpoint; the same signal also leaked that OpenAI's `text-embedding-3-small` is a decoder-only Transformer, otherwise undocumented [@gu-2025-auditing]. vLLM's own chunk-based PagedAttention prefix cache carried a CVE-assigned instance (CVE-2025-46570): with a 1-token shared prefix, hit/miss classification reached a ROC AUC of 0.571; at 8 tokens, AUC rose to 0.99 on LLaMA2-70B-GPTQ [@vllm-2025-cve].

### Provider and framework mitigations: isolation, salting and selective sharing

The general fix is to stop sharing cache state across mutually distrustful principals, or to make sharing decisions unobservable to clients. vLLM's response to CVE-2025-46570 was an optional per-request `cache_salt`, injected into the hash of a request's first KV block so only requests carrying the same salt can reuse each other's blocks, shipped in v0.9.0 [@vllm-2025-cve; @vllm-prefix-design]. The RFC that proposed this mechanism labeled it the "single-barrier" design – one salt per request – and, in the same proposal, described a "multi-barrier" alternative that instead salts only a tenant-specific suffix while leaving a genuinely shared prefix unsalted [@vllm-2025-rfc16016]. The single-barrier design fully isolates tenants but is blunt: with 256 tenants sharing one system prompt, per-tenant salting forces 256x duplicate prefill of that prompt's blocks, since salted tenants can no longer reuse each other's blocks at all [@vllm-2026-hiersalt]. The multi-barrier extension was meant to recover that lost reuse; the original RFC closed its multi-barrier half as future work ("getting back to multi barrier design...only if needed"), a full hierarchical implementation was proposed roughly a year later and closed unreviewed after five months of inactivity, and as of September 2026 a narrower, core-only reimplementation of the multi-barrier hashing contract remains open and unmerged, with the request-level API and per-message salt mapping not yet built on top of it [@vllm-2025-rfc16016; @vllm-2026-saltregions]. vLLM's cache key also folds `cache_salt` in with block token content, LoRA adapter ID, and multimodal input hashes, making it a content-addressed structure; the project explicitly documents that swapping its default cryptographic hash (SHA-256) for a faster non-cryptographic one (xxHash) "increases the risk of hash collisions, which can cause undefined behavior or even leak private information in multi-tenant environments" [@vllm-prefix-design] – a direct, vendor-documented trade-off between hashing speed and cross-tenant isolation. Hosted APIs mitigate the same risk structurally rather than via client-supplied salts: OpenAI scopes caches to the organization, never shared across organizations, and exposes a `prompt_cache_key` explicitly described as helping "prevent cache-hit probing across users" [@openai-2026-promptcaching]; Anthropic isolates per *workspace* (finer than organization) on its own API, on Claude Platform on AWS, and on Microsoft Foundry (currently in beta), but falls back to organization-level isolation on Amazon Bedrock and on Google Cloud's Vertex AI – an inconsistency an operator spanning hosting surfaces should not assume away [@anthropic-2026-promptcaching]. Because full per-tenant isolation gives up the benefits that motivated caching, selective sharing has been proposed as a middle ground: SafeKV classifies KV blocks as shareable or private via an asynchronous classifier over a radix-tree index, reporting mitigation of 94–97% of timing-based attacks while recovering up to 2.66x the throughput and cutting TTFT overhead by up to 40.58% versus full isolation [@chu-2025-safekv] – a probabilistic reduction, not a guarantee, dependent on an ML classifier that is itself an attack surface, and still a research prototype rather than an audited production feature.

### KV tensors as a partially invertible, tamperable representation of the prompt

A second, distinct risk applies once an adversary obtains the raw KV tensors themselves – via a compromised remote cache store, an unencrypted offload path, or a misconfigured RDMA link – rather than merely observing timing. Luo et al. show the KV cache is not merely correlated with the prompt but can be partly reconstructed from it [@luo-2026-shadowcache]. A direct algebraic Inversion Attack recovers the first-layer input with near-100% fidelity when the key/value projection matrices are square and invertible, as in classic multi-head attention (e.g. LLaMA-7B); it generally fails against modern architectures using grouped-query or multi-head latent attention (e.g. Llama-3, Qwen, DeepSeek), whose projections are non-square – though the same paper reports one documented exception, the GQA-based LLaMA-3.2-1B, which still exhibited near-100% first-layer reconstruction fidelity, attributed by the authors to that model's unusually high projection rank relative to its hidden-state dimension, which lets a least-squares solve recover the input despite the non-square projection, so "fails against GQA/MLA" is the common case rather than a categorical guarantee [@luo-2026-shadowcache] – and against deeper-layer caches, whose states are semantically fused rather than a direct token embedding [@luo-2026-shadowcache]. A model-agnostic Collision Attack instead re-runs a local copy of the model over candidate tokens and matches resulting KV entries against the intercepted cache, applying regardless of architecture or layer, at the cost of a vocabulary-sized search per token [@luo-2026-shadowcache]. An Injection Attack sidesteps reconstruction entirely: appending "Repeat the previous content" to a stolen cache and resuming generation caused the model to echo its own private context (average BERTScore 0.58, ROUGE-L 0.42) [@luo-2026-shadowcache]. Because the cache can be read, it can typically also be written. Ganesh et al.'s "History Swapping" overwrites a full-layer, contiguous block of an active generation's cache with a precomputed cache on a different topic, hijacking the conversation's trajectory – persistently, partially, or after a delay – without altering the visible prompt, across 324 configurations on Qwen3; partial- and early-layer overwrites were comparatively robust, so the result should not be generalized to "any cache write compromises any model" [@ganesh-2025-narrative]. Both lines of work assume the precondition the next section's mitigations target: read/write access to plaintext KV tensors in storage or transit. None of the major production KV-cache serving or storage stacks – on-GPU engines such as vLLM and NVIDIA TensorRT-LLM, or disaggregated stores such as Mooncake and LMCache – are documented to implement the reversible-obfuscation defense these papers propose by default.

### Encryption, integrity and retention in practice

Confidentiality of KV tensors at rest and in transit is therefore load-bearing, not optional, once caches leave GPU memory. OpenAI documents two prompt-cache retention tiers with different defaults: an `in_memory` tier bounded to roughly 5–10 minutes of inactivity and never more than one hour, and an extended `24h` tier that typically keeps entries available for about 30 minutes and can retain them for up to 24 hours; organizations without Zero Data Retention enabled default to the 24-hour tier, and only organizations with Zero Data Retention enabled default to the shorter in-memory tier [@openai-2026-promptcaching]. OpenAI documents that prompt caching "may store encrypted key/value tensors in GPU-local storage as application state" [@openai-2026-promptcaching; @openai-2024-promptcaching-blog] – that phrasing is the vendor's own hedge and should be read as a lower bound, not a blanket guarantee across every model, tier and region; in particular, for the majority of organizations that have not enabled Zero Data Retention, the retention ceiling to plan around is 24 hours, not one hour. Anthropic's default TTL is 5 minutes, refreshed on each hit, with an opt-in 1-hour TTL priced at 2x the base input-token rate versus 1.25x for the 5-minute default – about 1.6x the 5-minute cache-write price, not literally double it; Bedrock documents the same TTL options with per-model minimum token counts per checkpoint [@anthropic-2026-promptcaching]. The self-hosted reference stacks this whitepaper surveys for offload and persistence expose far less structured protection. Mooncake Store's public deployment and client-configuration references document only transport, host and buffer-size parameters for cross-machine KV transfer (RDMA/TCP protocol, RDMA device selection, segment and buffer sizes), with no authentication or encryption field anywhere in that surface for the Master/Client data path itself [@mooncake-2026-deployguide; @mooncake-2026-configpy]; the one credential-bearing option documented in the public surface, `MC_REDIS_PASSWORD`, authenticates only to the optional Redis metadata backend, not the RDMA/TCP data plane that actually carries KV bytes [@mooncake-2026-transferengine]. Separately, Mooncake Store's own design documentation describes a (now legacy, superseded by a newer SSD-offload subsystem) tiered mode that asynchronously backs up in-memory KV objects to a distributed file system keyed by the caller-supplied object key – in practice a content-derived hash when Mooncake is driven by a prefix-caching client such as LMCache – with no mention of at-rest encryption anywhere in that design [@mooncake-store-docs]. That is an absence in the public reference, not proof no such option exists anywhere in the codebase, but it means an operator layering Mooncake, LMCache, or a similar disaggregated store into a multi-tenant deployment must add transport security (mutual TLS at a gateway, a private VPC, IPsec on the RDMA fabric) and at-rest encryption themselves; none of it is on by default. Retention deserves the same scrutiny as encryption: a KV cache with a bounded but nonzero TTL, built from – and, per the inversion results above, sometimes recoverable to – the original prompt, is a store of derived personal or proprietary data. It is easy to omit from data-retention and right-to-erasure processes that target request logs and application databases but never look inside the inference engine's own memory hierarchy; an erasure request honored in the application layer while a matching KV block still lives in a shared cache for the next several minutes (or, on an offloaded/persistent path, considerably longer, and up to 24 hours on OpenAI's non-ZDR default tier) is not actually honored.

### Checklist for operators

- Treat unsalted, globally shared prefix/KV caching across mutually distrustful tenants as unsafe by default; enable per-tenant isolation (`cache_salt`, an org/workspace-scoped hosted API) before enabling cross-request reuse.
- If isolating every tenant forces unacceptable recompute of a genuinely shared prefix, scope isolation to the tenant-specific suffix rather than disabling caching outright, and verify isolation with a cache-hit-rate or timing conformance test – hash-equality unit tests alone don't prove no cross-tenant reuse at serving time.
- Use a cryptographic hash (SHA-256 or equivalent) for cache keys in multi-tenant deployments; treat a switch to a faster non-cryptographic hash as a security decision, not just a performance one.
- Encrypt KV tensors at rest and in transit at every hop they leave GPU memory – PCIe offload, NVMe spill, RDMA transfers, remote KV stores – since the reference implementations surveyed here do not enable this by default.
- Rate-limit and monitor for cache-hit probing patterns (bursts of near-duplicate requests, systematic TTFT fingerprinting), as with credential-stuffing or enumeration attacks.
- Where full isolation is too costly, consider selective/classified sharing as a middle ground, but budget it as a probabilistic mitigation (reported in the 90s of percent, not a guarantee) whose classifier is itself part of the attack surface.
- Document retention windows and cache scope (user/workspace/organization) for every caching layer, and confirm data-deletion and right-to-erasure processes actually reach the KV cache, not only logs and databases.

## The Cache as an Editable State: Attention Interventions (NaLa)

Every optimization considered so far treats the KV cache as a performance structure to be paged, quantized, offloaded or replicated, while leaving its *contents* untouched: the cache is a faithful record of what the model actually computed during prefill, and inference reads it unmodified. A separate line of interpretability and steering work treats the cache differently: as the literal, per-token record of what each layer currently has available to attend to, and therefore as a surface that can be read and edited at inference time to test or correct a model's behavior without touching its weights or its prompt. This section examines that idea through a concrete public case study, NaLa, an MIT-licensed research tool from Hassana Labs, together with the accompanying mathematics of exact attention responses [@huang-2026-nala; @huang-2026-rope; @huang-2026-secant]. As of September 2026 this is recent, actively developed research code rather than a serving-system feature, and the evidence behind it is narrower than the mechanism itself; both the capability and its limits are described below.

### What a cache intervention is

A *cache intervention*, in this sense, edits the keys and/or values that one query's attention computation reads at one layer, for that read only, rather than modifying the stored K/V tensors that persist in the cache. NaLa's published interface exposes two such edits at the granularity of one layer and one or more token positions: *deletion*, which excludes selected cache entries from the attention read while keeping the causal complement's softmax normalizer intact, and *reweighting*, which multiplies a span's unnormalized attention logits by a factor before renormalizing over the full causal bank — a factor below one suppresses a span, above one boosts it [@huang-2026-nala]. Execution keeps every branch on an independent copy of the shared prefix cache, so a candidate edit cannot leak into another candidate or into the underlying stored state [@huang-2026-nala]. The accompanying paper's calculus additionally covers finite positional (rotary) displacements and joint key–value content edits, though the shipped command-line tool's documented interface centers on deletion and reweighting [@huang-2026-rope].

This is a narrower claim than either prompt engineering or weight editing. Prompt engineering changes what gets computed before it is cached; a cache intervention changes what is read from an already-computed cache, leaving the underlying prompt and parameters untouched, which is why the same edit can be tested, compared against a control, and discarded without retraining or re-prompting [@huang-2026-nala]. It is also narrower than residual-stream activation steering, which adds a fixed direction to one hand-selected layer's activations at every generated token to shift a global output property such as sentiment or topic [@turner-2023-actadd]; a cache intervention instead edits specific cached entries at one layer for one query, targeting *which tokens are attended to* rather than adding a global bias to the representation.

### Exact response versus first-order attribution

Scoring a candidate edit requires predicting how the model's eventual output would change — ordinarily this means executing the edit and re-running the forward pass, which is prohibitive when there are tens of thousands of candidates. The standard cheap alternative, attribution patching, approximates a component's causal effect with a linear approximation: two forward passes (clean and corrupted) and a backward pass, rather than a full re-execution per candidate [@syed-2024-attribution]. AtP\* refines this approximation to correct specific failure modes of the naive linear version while keeping its cost profile [@kramar-2024-atp].

NaLa's underlying identity instead gives the *exact* change in a single query's attention output for a finite edit, using the exponential divided difference $\varphi_1(B) = \int_0^1 e^{tB}\,dt$, which for a scalar argument reduces to $\rho(s) = (e^s-1)/s$ (with $\rho(0)=1$) — the same divided difference that connects a finite rotary displacement, $z(p+\delta) - z(p) = \delta A \varphi_1(\delta A) z(p)$, to the corresponding softmax score change [@huang-2026-rope; @huang-2026-secant]. Softmax is not linearized and RoPE is not removed; the identity is exact for the edited attention write itself. Predicting the *downstream* effect on an answer or a loss still requires contracting that exact local response with a frozen baseline gradient obtained from one backward pass, and this is where approximation re-enters: the local response is exact, but its propagation through the remaining network layers is not [@huang-2026-rope].

On the authors' own held-out evaluation, retaining this exact local response rather than a first-order approximation makes a measurable quantitative difference:

| Study | Executed edits | Metric | Reported result |
| --- | ---: | --- | ---: |
| Finite positional (rotary) edits | 92,160 (768 held-out prompt sets) | sign accuracy | 95.36–96.52% |
| Finite positional (rotary) edits | 92,160 (768 held-out prompt sets) | MAE vs. a linearized (Jacobian) baseline | 73.6–82.5% lower |
| Joint key–value edits | 5,120 (2 Qwen sizes × 2 tasks × multiple layers) | MAE vs. separately attributed key and value effects | more than 9× lower, every setting |

These figures are the authors' own reported evaluation on their own held-out sets [@huang-2026-rope]. The independent replication described below reproduced the recorded repair case, not these held-out studies.

### Cost: one backward pass, many candidates

The practical payoff of an exact, closed-form response is that scoring does not require re-running the model per candidate. NaLa's capture step performs a no-grad forward pass over the prefix, one gradient-enabled forward pass for the query being edited, and a single backward pass that yields gradients for every layer under consideration; after that, scoring any number of candidate edits is closed-form arithmetic over the captured per-token statistics, making zero further calls to the model [@huang-2026-nala]. Naively scoring $C$ candidates by execution costs $C$ forward passes; this approach instead costs a fixed, small number of forward/backward passes for the capture plus $O(C)$ arithmetic, with actual model execution reserved for the handful of top-ranked candidates chosen for verification. No public wall-clock or memory benchmark of the capture step itself against plain, no-grad inference was found; the efficiency argument here is structural — a fixed capture cost independent of $C$ versus a per-candidate cost that scales with $C$ — rather than an empirically measured latency or memory figure.

The published illustration of this is a small coding-repair case: a model calling a removed API function, checked against six fixed unit tests. Scoring covered 109,080 candidate edits — every token position, at every layer, under fifteen edit templates — from that single capture, and only the top-ranked candidate was actually executed:

| Branch | Result on the fixed test suite |
| --- | ---: |
| Ordinary generation | 0/6 |
| Top-ranked attention edit (of 109,080 scored candidates) | 6/6 |

The authors are explicit that this is one adaptively selected synthetic task, not a benchmark [@huang-2026-nala].

### Scope and what has not been shown

The published scope is narrow along several axes at once. Native support is limited to FP32 weights under eager (unfused) full causal attention with fixed, unscaled RoPE, on the Qwen2 and Qwen2.5 architectures; recorded results are CPU-only, and a 7B-scale run on a GPU is documented as prepared but not validated [@huang-2026-nala]. Each candidate edits one layer; deletion masks an entry rather than shortening the prompt or shifting token positions, so it changes what is attended to, not what exists in the sequence [@huang-2026-nala]. And the central quantitative claims above are the authors' own measurements against their own held-out sets, not an independent audit — a materially weaker evidentiary standing than the peer-reviewed baselines this whitepaper otherwise draws on.

### Independent replication: what survives

An independent replication fork of NaLa, whose documentation was rewritten in place wherever a claim did not survive, supplies the evidence that the public repositories lack [@elementalcollision-2026-nalarepl]. Its findings sharpen both the capability and its limits:

- **The mechanism and the recorded case reproduce.** A full 24-layer re-capture of the repair case on different hardware and a different PyTorch build matched the recorded baseline margin (−6.683786 vs. −6.683828), the top-ranked predicted gain (+11.360970 vs. +11.360963), the executed gain (+9.398861 vs. +9.3989) and the winning site (layer 21, row 79, odds ×64). The attention identity's residual stays at about $10^{-14}$ at every size from 0.5B to 7B, once a tautological check in an earlier version of the harness was corrected.
- **The headline count overstates the search.** The 109,080 candidates are 7,272 distinct token/layer sites under fifteen edit templates, seven of which belong to one monotone reweighting family; the tool's default template set gives 72,720. The distinct-site count is the more honest measure of the search breadth.
- **Exactness mattered for magnitude, not for the winner.** On the recorded case, a first-order (attribution-patching-style) score picks the same top candidate as the exact response. Over the exact top 1,000, however, the first-order score is a median 0.216× the exact value (a roughly five-fold underestimate), and in 18 of the 24 individual layers the two methods disagree on which candidate ranks first.
- **The case was selected from 107 attempts.** Of 107 case-construction attempts, 85 were already solved by a control before any attention edit was scored, 11 had invalid controls, and 10 reached an attention edit, of which one passed. The published case is that one.
- **The repair does not survive scale.** Run unchanged across ten checkpoints in three families, the repair reproduced only at Qwen2.5-0.5B and Qwen3-0.6B. It failed at 1.5B, 3B and 7B (Qwen2.5), 1.7B, 4B and 8B (Qwen3), and at SmolLM2-360M and 1.7B. The achievable gain shrinks with scale (from +9.4 to about +3.5 nats on Qwen2.5) while the deficit it has to close does not. A pre-registered prediction that at least one checkpoint below 1B would repair was falsified: SmolLM2-360M, smaller than both repairing models, did not.
- **A favourable prediction is necessary, not sufficient.** In a pre-registered multi-site experiment with 48 executed edits, no edit repaired the program without its margin crossing zero, but eleven edits crossed zero (after-margins +0.913 to +4.891) and still failed. Nothing measured so far predicts which crossings produce a passing program.
- **A diagnostic claim was withdrawn.** A second, two-document "stale context" case, earlier offered as evidence that the method distinguishes *attending to the wrong tokens* from *attending correctly and deciding wrongly*, could not be reproduced from any fixture, script or recorded measurement and was removed; that diagnostic claim is unevidenced.

Taken together, the replication supports the mathematics and the tooling, and supports the repair as a real, reproducible event on two specific small checkpoints; it does not support treating attention editing as a general repair capability. The fork also extends the public tool (Qwen3 and fixed-RoPE Llama support, donor-copy key/value edits, a source-code repair controller, and an exact KV-row precision-restoration routine evaluated only on simulated quantization); these extensions are not part of the public release [@elementalcollision-2026-nalarepl].

### Systems implications

Treating the cache as editable rather than merely relocatable puts this idea in tension with exactly the optimizations covered earlier in this paper. Production serving systems already share KV cache blocks across requests with a common prefix, mapping several requests to the same physical block until one diverges, at which point that block is copied rather than shared further — the block-sharing and copy-on-write mechanism vLLM introduced for a single request's parallel-sampled or beam-searched output sequences [@vllm-blog] is generalized across separate requests by automatic prefix caching [@vllm-apc]. A per-read cache intervention is a deliberate, request-scoped divergence of precisely this kind: to keep other requests reading the unedited shared block, the affected entries must be copied into a private branch before the edited read, which is consistent with why NaLa's own execution model gives every branch an independent copy of the prefix cache rather than editing in place [@huang-2026-nala]. In a paged, prefix-sharing serving engine, an intervention therefore forces the same copy-on-write fork that prefix caching exists to avoid, so the two features pull in opposite directions unless an intervention is scoped tightly enough that only the diverging request pays the copy cost.

A second implication concerns provenance. Because an edit changes what is read without changing the stored tensors, a persisted cache — of the kind considered earlier for fault tolerance and checkpointing [@dejavu] — would be bit-identical in shape whether or not an intervention occurred; only a separate record of which layer, which entries, and which edit were applied could preserve the fact that a resumed generation is not what an unedited forward pass would have produced. No such persistence or provenance mechanism is part of the published tool, which operates on ephemeral, in-process cache copies rather than durable state [@huang-2026-nala].

Third, the intervention as published depends on the cache being present as directly addressable, full-precision per-token tensors: the documented scope is FP32 under eager attention [@huang-2026-nala]. That is a different execution path from the block-table indirection of paged attention [@vllm-blog] or from a quantized cache holding 2-bit [@kivi; @logquant] or FP8 [@vllm-fp8] entries rather than full-precision keys and values. Porting a per-read intervention of this kind into a paged, fused, or quantized production layout would require, at minimum, an unfused reference attention path over the specific entries being edited and dequantization of the affected cache blocks before the edit — a materially different, and slower, code path than the ones production serving engines are built around. Nothing in the public record indicates this integration exists yet; the mechanism has been demonstrated as a diagnostic and repair tool on small, single-request, CPU workloads, not as a production serving capability.

## Appendix A: KV Cache Sizing Calculator

`tools/kv_calc.py` is a dependency-free Python 3 script that computes transformer KV cache size -- bytes per token and totals for a given context length, batch size, and storage dtype -- for a built-in table of eleven open-weight models spanning three cache-shaping mechanisms (including Mistral 7B v0.1, kept as the canonical example of a uniform sliding window, alongside more recent releases): plain grouped-query attention (bytes/token/layer = $2 \cdot n_{kv} \cdot d_{head} \cdot s$), DeepSeek-style Multi-head Latent Attention (bytes/token/layer = $(d_c + d_h^R) \cdot s$, independent of head count, per the formula in DeepSeek-V2's Table 1 [@deepseek-2024-mla]), and hybrid models that interleave full-attention layers with sliding-window layers whose cache stops growing once the sequence exceeds the window (Mistral 7B's uniform window, and Gemma 2/3's and gpt-oss's local/global interleaving). Run `python3 tools/kv_calc.py --list` to see all eleven models, their architecture parameters, and each model's own documented or configured maximum context length (each sourced from a public Hugging Face `config.json` -- Llama 3 8B and 3.1 70B [@meta-2024-llama3-8b-cfg; @meta-2024-llama31-70b-cfg], Mistral 7B v0.1 [@mistralai-2023-7b-cfg; @jiang-2023-mistral7b], Qwen2.5-7B and Qwen3-8B [@alibaba-2024-qwen25-7b-cfg; @alibaba-2025-qwen3-8b-cfg], DeepSeek-V2/V3 and Kimi K2 Instruct [@deepseek-2024-v2-cfg; @deepseek-2024-v3-cfg; @moonshotai-2025-kimik2-cfg], and Gemma 2 9B and Gemma 3 27B [@google-2024-gemma2-9b-cfg; @google-2025-gemma3-27b-cfg], with gpt-oss-20b's explicit alternating layer pattern [@openai-2025-gptoss-20b-cfg]); `python3 tools/kv_calc.py --model llama3-8b --tokens 128k --batch 4 --dtype fp8` to size one model at a specific context/batch/dtype; or omit `--model` and add `--markdown` to print a comparison table across the whole built-in set, as below. `--tokens` accepts binary-prefix shorthand (`4096`, `128k`, `1m`).

FP8 storage (1 byte/element) halves every BF16 figure, independent of any model's own weight dtype -- including DeepSeek-V3 and Kimi K2 Instruct, whose public config.json files carry an `fp8` `quantization_config` for their released *weights*. This tool's `native_dtype="bf16"` default for those two describes the KV-cache/activation dtype it assumes for sizing, not a claim about the checkpoint's own weight storage format; whether their weight-level FP8 quantization extends to the attention/KV path is not established from config.json alone. gpt-oss-20b's own config makes the general pattern concrete: its `quantization_config` excludes `model.layers.*.self_attn` from mxfp4 conversion, i.e. OpenAI's config documents attention as running outside its low-precision weight format.

At 128K tokens, Mistral 7B v0.1's 4096-token uniform sliding window and gpt-oss-20b's 128-token/1:1 local:global design cap their caches far below any uncapped GQA model of comparable size, at the cost of no layer (Mistral) or half the layers (gpt-oss) retaining exact long-range token-level context -- though of the two, Mistral's design is the more aggressive cache reducer in practice: its all-sliding architecture caps the total at 512 MiB with zero marginal growth past 4096 tokens, versus gpt-oss-20b's 3.00 GiB and continued linear growth from its 12 full-attention layers, despite gpt-oss's smaller raw window number (128 vs 4096). The three MLA models cluster around 8-9 GiB despite layer counts (60-61) well beyond Llama 3 8B's 32, and not far off Llama 3.1 70B's 80, consistent with DeepSeek-V2's own reported "equal to GQA with only 2.25 groups" characterization [@deepseek-2024-mla]. Gemma 3's smaller 1024-token window and 5:1 local:global ratio (versus Gemma 2's 4096-token window and 1:1 ratio [@google-2025-gemma3]) roughly halve its total at this length despite having 20 more layers than Gemma 2 -- the two models happen to have identical bytes/layer/position (8,192 B), since $8 \times 256 = 16 \times 128 = 2{,}048$ cached elements per layer either way, which isolates the window/ratio effect rather than reflecting a general property of the Gemma 2 -> Gemma 3 architecture change. (Google's own ablation of this ratio/window change, on a 2B text-only model at a 32K-token context, shows KV-cache memory overhead falling from ~60% to under 15% with a 1:3 ratio and a 1024-token window [@google-2025-gemma3] -- the closest ablated setting to, but not the same configuration as, the 5:1 ratio profiled in the table above; the report does not give a single overhead percentage for the shipped 5:1 architecture at 32K.) Bytes/token above is exact and constant for GQA and MLA rows; for the hybrid rows it is an average over the full 128K sequence, since sliding-window layers stop accumulating once tokens exceed their window while full layers keep growing (`kv_cache_bytes()` also reports the marginal, steady-state bytes/token separately).
